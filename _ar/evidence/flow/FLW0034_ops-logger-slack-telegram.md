## B. Behavior Digest
- Trigger:
  - **Passive log-pipeline listener (both)** — because each service carries the Drupal `logger` service tag, Drupal registers it with `logger.factory` (`Drupal\Core\Logger\LoggerChannelFactory`) as a **global log sink**: every `\Drupal::logger(<channel>)->{level}(...)` / `LoggerChannel::log()` record in the whole application is fanned out to *all* tagged logger services, including these two. `Confirmed` (tag semantics + `LoggerInterface::log()` implementation).
  - **Direct forced-alert calls (both)** — in addition to the passive fan-out, ~48 call sites invoke `\Drupal::service('logger.telegram')->log(3, "<msg>")` or `\Drupal::service('logger.slack')->log(3, "<msg>")` **directly with an explicit RFC level `3` (ERROR)** to force an ops alert regardless of the emitting channel's own level. Direct callers span payments/finance/cron/queue code — e.g. `comgate/src/ComgateCron.php:41`, `netopia/src/NetopiaService.php`, `netopia/src/NetopiaCron.php`, `netopia/src/Commands/NetopiaCommands.php`, `maib/src/MaibService.php:40`, `maib/src/Commands/MaibCommands.php:79`, `accounting/src/Form/BankForm.php:149,315`, `transaction/transaction.module:114,142`, `transaction/src/Plugin/rest/resource/v32/TransactionResource.php:212,319`, `transaction/src/Plugin/rest/resource/{,v32/}TransactionVoucherResource.php:218`, `application/src/ApplicationCron.php`, `campaign/src/CampaignCron.php`, `voucher/src/VoucherCron.php`, `patron_base/src/PatronBaseMauticCron.php`, `patron_base/src/Plugin/QueueWorker/MauticQueue.php`, `patron_search/src/{PatronSearchCron.php,Plugin/QueueWorker/EsUploadQueue.php,Command/EsUploadCommand.php}`, `organisation/src/OrganisationCron.php`, and numerous `account/src/Plugin/rest/resource/**` resources. `Confirmed` (grep of `logger.slack`/`logger.telegram` direct call sites).
  - **`sendMessageToZoneChannel()` "activity feed" calls (Slack only)** — ~25 sites call `\Drupal::service('logger.slack')->sendMessageToZoneChannel($user, '<activity text>', $attachments)` to post user-activity events (login, profile-photo upload, password change, activation-link opened, new lead created, contact-form submitted). See Failure Modes: this method body is **empty** (`SlackLogger.php:85-86`) — these calls are silent no-ops. `Confirmed`.
- Preconditions:
  - Both modules must be enabled. **Config evidence shows both weighted `0` in `config/core.extension.yml` (`slack_integration: 0`, `telegram_integration: 0`)** — present in the module list; enabled-state at runtime not otherwise verified. `Confirmed` (listed), `Hypothesis` (actually active in prod).
  - **Slack**: config array `Settings::get('slack')` must exist and contain a non-empty key for the resolved webhook (`webhook_url_errors` for ERROR, `webhook_url_checks` for CRITICAL) (`SlackLogger.php:57,65`). Values are **not hardcoded** — read from `settings.php`/`Settings`; all URLs `<redacted>`.
  - **Telegram**: config array `Settings::get('telegram')` must supply `chat_id` and `bot_id` (`TelegramLogger.php:31-34`); both must be truthy or the call returns without posting. Token/chat id `<redacted>`.
  - Level gate (both): the record's numeric RFC level must satisfy `$level <= 3`, i.e. EMERGENCY(0)/ALERT(1)/CRITICAL(2)/ERROR(3) pass; WARNING(4) and below (NOTICE/INFO/DEBUG) are dropped (`SlackLogger.php:65`, `TelegramLogger.php:35`). Slack additionally has an outer `switch` that **returns early for anything except ERROR/CRITICAL** (`SlackLogger.php:47-56`), so EMERGENCY(0)/ALERT(1) never reach Slack even though they pass the numeric `<=3` test.
- Main Steps:
  1. **Slack** (`SlackLogger::log()`, `SlackLogger.php:46`) — (a) `switch ($level)`: ERROR→`$webhook_url = 'webhook_url_errors'`, CRITICAL→`'webhook_url_checks'`, `default: return` (`:47-56`); (b) load `$config = Settings::get('slack')` (`:57`); (c) `trim` the message, apply `strtr($message, $context)` placeholder substitution, `strip_tags(substr(...,0,1800))` → `$message_safe` (`:58-60`); (d) if `$message_safe` empty → return (`:62`); (e) if `$level <= 3 && !empty($config[$webhook_url])` → `\Drupal::httpClient()->post($config[$webhook_url], ['json' => ['text' => $message_safe]])` (`:65-72`).
  2. **Telegram** (`TelegramLogger::log()`, `TelegramLogger.php:30`) — (a) `$config = Settings::get('telegram')` (`:31`); (b) read `$chatId`/`$botId` (`:33-34`); (c) if `$level <= 3 && $chatId && $botId && $message` (`:35`): apply `strtr($message,$context)` + `strip_tags(substr(...,0,1800))` → `$messageSafe` (`:36-37`); (d) build URL `https://api.telegram.org/bot{botId}/sendMessage` (bot id `<redacted>`) (`:41`); (e) `\Drupal::httpClient()->post($url, ['headers'=>{Accept, Content-Type: x-www-form-urlencoded}, 'form_params'=>['text'=>$messageSafe,'chat_id'=>$chatId]])` (`:42-50`); (f) if HTTP status != 200, log the response body to Drupal channel `telegram` at INFO (`:51-53`).
  3. **Fan-out multiplicity** — a single ERROR/CRITICAL record emitted anywhere in the app is delivered to **both** channels (each tagged `logger`) plus Drupal's own dblog/syslog; direct `->log(3,...)` calls target exactly one channel object (the one resolved by the service id) and do **not** fan out to the other. `Confirmed`.
- Postconditions:
  - One outbound HTTP POST per qualifying record per channel (best effort). No local persistence, no queue, no dedup/rate-limit state written.
  - No domain-entity mutation. No status transition. This is a pure side-effect alerting adapter.
- Side Effects:
  - **Outbound HTTP** to Slack incoming-webhook URL (`<redacted>`) and to Telegram Bot API (`https://api.telegram.org/bot<redacted>/sendMessage`). See Integration Calls.
  - **Self-logging on failure** — Slack catches `\Exception`/`\Throwable` and writes `\Drupal::logger('slack')->error(...)` (`SlackLogger.php:73-77`); Telegram catches `\Exception` and writes `\Drupal::logger('telegram')->info(...)` (`TelegramLogger.php:55-58`) and also on non-200 (`:52`). **Risk (Async/re-entrancy):** the Slack failure handler logs at `error()` (level 3) into the same global log pipeline this service subscribes to — a Slack outage can re-trigger `SlackLogger::log()` for the `slack` channel record, and if `webhook_url_errors` is also failing this can recurse/amplify. `Hypothesis` (depends on channel routing config; not directly evidenced as observed).
  - **Message truncation** to 1800 chars and `strip_tags`/tag-stripping (both) — long stack traces are cut; HTML/markup removed. `Confirmed`.
  - **No side effect for `sendMessageToZoneChannel()`** — method is empty; the ~25 Slack "activity feed" posts produce nothing. `Confirmed` (Data-Loss / dead-behavior).
- Integration Calls:
  - **Slack Incoming Webhook** — `httpClient->post(<redacted webhook_url>, json:{text})`. Endpoint per-level (`webhook_url_errors` / `webhook_url_checks`). Matches [../../repo-map/integrations.md](../../repo-map/integrations.md):61. `Confirmed`.
  - **Telegram Bot API** — `httpClient->post(https://api.telegram.org/bot<redacted>/sendMessage, form_params:{text,chat_id})`. Matches [../../repo-map/integrations.md](../../repo-map/integrations.md):62. `Confirmed`.
  - No auth/retry/timeout options are set on either `->post()` call → uses Guzzle/`\Drupal::httpClient()` defaults (blocking, default timeout). `Confirmed` (no options array beyond payload/headers).
- Failure Modes:
  - **Blocking synchronous HTTP on the hot path (Async/Performance)** — despite the `slack_queue` created by `slack_integration_update_8001()` (`slack_integration.install:5-8`) and commented-out `QueueFactory` constructor (`SlackLogger.php:37-40`) / commented `#arguments: ['@queue']` (services.yml:4), **the queue is never used** — the post is synchronous inside `log()`. Because this runs as a logger channel, every ERROR/CRITICAL anywhere in the request blocks on an outbound Slack+Telegram POST (no timeout override), which can slow or stall request/cron completion during a Slack/Telegram outage or slow response. `Confirmed` (Async / operational).
  - **`sendMessageToZoneChannel()` is a no-op — silent loss of ~25 activity signals (Data-Loss / dead behavior)** — the method body is empty (`SlackLogger.php:85-86`) yet is called with meaningful audit content (logins, password changes, profile updates, new-lead creation, contact-form submissions) from `account/**`, `application/**`, `contact/**`, `feedback/**`, `transaction/src/Entity/TransactionEntity.php:801`. None of these reach Slack. Anyone relying on a Slack "zone" activity feed sees nothing. `Confirmed`.
  - **Best-effort delivery / no retry / no persistence** — a failed POST is only self-logged; the alert is lost. There is no queue, no backoff, no dedup, no dead-letter. `Confirmed`.
  - **Config-absent silent disable** — if `Settings::get('slack')`/`('telegram')` is unset or missing the resolved key, `log()` returns without posting and **without any error** (`SlackLogger.php:65` empty-check; `TelegramLogger.php:35` truthy guards). Ops alerting can be silently off in an environment that forgot to configure it. `Confirmed`.
  - **Level-routing quirks (Security/Boundary — noise vs. drop)** — (1) Slack routes ERROR→errors-webhook and CRITICAL→checks-webhook, but EMERGENCY(0)/ALERT(1) hit `default: return` and are dropped entirely (`:54-55`); (2) the many direct `->log(3, ...)` calls hard-code ERROR for what are frequently *informational* operational notices (e.g. "Pocet plateb starsich 7 dni…", `transaction.module:142`; "Missing ext_trans_id…", `ComgateCron.php:41`), so genuine errors and routine status pings share the same ERROR webhook — alert-fatigue / signal dilution. `Confirmed` (behavior), `Hypothesis` (operational impact).
  - **PII / sensitive data in outbound alerts (Security/Legal-GDPR)** — direct callers interpolate user identifiers and business data into the message before it is POSTed to Slack/Telegram (e.g. "Users without supporter role: <ids>", `transaction.module:114`; transaction ids and exception bodies incl. `json_encode($data)`, `TransactionResource.php:319`; MAIB/comgate error payloads). `strip_tags`+1800-char truncation do not redact PII. Sensitive current-state data can leave the platform boundary to third-party chat services. `Confirmed` (data egress path), `Partial` (exact PII content varies per call site).
  - **Telegram class-docblock mislabel** — `TelegramLogger.php:12-13` docblock says `Class SlackLogger` (copy-paste); harmless but confirms the two were cloned. Also `TelegramLogger` has **no per-level webhook switch** — every passing level goes to the single bot chat. `Confirmed` (cosmetic + behavioral note).
  - **Re-entrant failure logging (Async)** — see Side Effects; Slack's `catch` re-logs at `error()`. `Hypothesis`.
  - **Unbounded fan-out cost** — with both channels tagged, and dblog/syslog also active, a burst of ERRORs (e.g. a failing cron looping) multiplies into a burst of external POSTs with no throttle. `Confirmed` (structural), `Hypothesis` (observed).

  - **None.** No AR domain entity is created/updated/deleted. The only "writes" are outbound HTTP payloads to Slack/Telegram and self-referential Drupal log records (`slack`/`telegram` channels) on failure — not entity mutations.
- Entities Read:
  - **None (no entity/DB reads in this flow).** Inputs are the log `$level`, `$message`, `$context` array, and `Settings::get('slack'|'telegram')` config. `sendMessageToZoneChannel($user, ...)` receives a user object from the caller but the method body ignores it. `Confirmed`.
- Constraints involved:
  - None enforced by this flow. No validation, no uniqueness, no idempotency key. Message length is clamped to 1800 chars (formatting, not a data constraint).
- Multi-tenant scope assumptions:
  - **No country/tenant (CZ/RO/MD) partitioning of alerts.** Slack uses two global webhooks (errors/checks); Telegram uses a single global `chat_id`/`bot_id`. All-region errors land in the same channel(s); alerts are **not** segmented per country/domain. `Confirmed` (no tenant predicate in either `log()`). Multi-tenant/boundary concern for a CZ/RO/MD platform: RO/MD operational alerts (incl. localized/PII text, cf. Cyrillic message at `MaibCommands.php:79`) flow to the same CZ-oriented ops channels.
