## B. Behavior Digest
- Trigger: Admin/coordinator UI actions on the application "Contract" tab (`contract.application` `listContract`), each a GET route; final step is the fundraiser (žadatel) submitting the sign form in the self-service zone.
- Preconditions: `listContract` (`ApplicationContractController.php:21`) gates creation on: fundraiser aprofile filled, `contract_type` chosen, fundraiser set, patron set (unless `skipPatronApplication()`), coordinator set (`getCoordinator`); child is warned but not blocking. Creation route needs `add contract entities`; checking `send contract to manager`; fundraiser send `send contract to fundraiser`. Sign route requires `_application_role: fundraiser` + `_application_status: TRUE` (`ApplicationAccessCheck`/`StatusAccessCheck`, `application/src/Access/`), UUID param-converter `application.uuid.paramconverter`.
- Main Steps:
  1. Create: `createContract` (`ApplicationContractController.php:124`) → `ContractEntity::create()`, `setPublicId($campaign)` (contract number), `fill($application)` loads `contract_template` by `contract_type`, applies `getReplacers` token substitution into `html`; `save()` triggers `preSave` PDF render; result linked on application `contract` field (appendix path appends to `appendix`). `contract_type === 'rental_contract'` also creates a rental agreement via `createRentalAgreement` (`:251`, which pre-signs manager).
  2. PDF render (entity hook): `ContractEntity::preSave` (`ContractEntity.php:116`) — if `html` non-empty, new `Mpdf(['tempDir'=>'/tmp'])`, `WriteHTML`, output to string, written to `public://contracts/smlouva-<md5>.pdf` via `file.repository`, id stored on `file` field.
  3. Manager check: `sendContractToManager` (`:358`) emails the checking address (`Settings::get('contract_checking_email')`) via `patron_base.smartmailing::handleMail(..., 'smlouvy_email_ke_kontrole', ...)` with download + send links; writes an application_log row; `setState('contract')`; `save()`.
  4. Manager signature + hand-off to fundraiser: `sendContractToFundraiser` (`:406`) — if `feature_digital_signature` enabled, `getContract()->signManager()` stamps manager image + current date into `html` (re-render), logs, `setState('waiting_signature')`, `save()`. Legacy path `sendContractToFundraiserOld` (`:456`) instead emails the ZZ (fundraiser) the PDF via `smlouvy_email_pro_zz` then `setState('waiting_signature')`.
  5. Digital-signature session build (listener): entering `waiting_signature` fires `notification` `ApplicationStatusUpdateSubscriber::updateApplicationStatus` (`notification/src/EventSubscriber/ApplicationStatusUpdateSubscriber.php:54`, gated on `feature_digital_signature`) — creates acceptance protocol, deactivates prior fundraiser sessions, and creates a new `application_session` (interface `custom`) carrying the contract markdown + PDF link for in-zone review/sign (no email in this path).
  6. Fundraiser sign: `ContractFundraiserSignForm::validateForm` (`:229`) requires typed full name == `getFundraiser()->getFullName()`; `submitForm` (`:236`) → `application->setState('contract_signed')->save()`, `signFundraiser($application)` writes `digital_signature` JSON, `createFundraiserSignatureConfirmation()` renders a QR/hash confirmation PDF, redirect to fundraiser applications view (AJAX swaps preview for signature summary).
- Postconditions: Contract entity persisted with `file` (PDF), `public_id`, `int_id`, and (post-sign) `digital_signature` JSON + `digital_signature_confirmation` PDF; application `contract` reference set; application state advanced `…→ contract → waiting_signature → contract_signed`; application_log + application_states rows appended; acceptance protocol contract created on entering `waiting_signature`.
- Side Effects: mPDF PDF generation ×2–3 (contract, signature confirmation, rental agreement) writing to `public://` (and transient `/tmp`); transactional email to manager (`smlouvy_email_ke_kontrole`) and — legacy path only — to fundraiser (`smlouvy_email_pro_zz`); application_log rows (`addApplicationLog`); application_states rows (`insertState` raw INSERT); new revisions on each application `save()`; fundraiser session (re)creation + deactivation of old sessions (digital path); debug logger writes to `contract` channel.
- Integration Calls: mPDF library (`Mpdf\Mpdf`, `ContractEntity::preSave`, `createFundraiserSignatureConfirmation`, `createRentalAgreement`); email via `patron_base.smartmailing` (`APIMailingService::handleMail` → SmartMailing template ids) in `sendContractToManager`/`sendContractToFundraiserOld`. Manager-signature images are hot-linked from `https://backend.patrondeti.cz/...` inside `signManager` (external URL fetched by mPDF at render).
- Failure Modes:
  - `signManager` calls `$this->save()` inside a method invoked from `sendContractToFundraiser` before `setState('waiting_signature')->save()` — no transaction wrapping the two saves; partial completion possible (Idempotence). `signManager` only stamps if the `<!--{manager-signature}-->` marker exists, so re-runs are self-idempotent, but re-clicking "Odeslat ZZ" still re-fires the status transition/listener.
  - No idempotence guard on `createContract`: calling create again on an application whose `contract` is already set overwrites the `contract` reference (main contract), abandoning the previous contract entity (Data Loss).
  - `getContractRow` / `sendContractToManager` dereference `contract->file->entity->getFileUri()` and `campaign->entity` with no null checks — fatal if PDF render failed or campaign unset.
  - Email send is best-effort: `sendContractToManager` guards on non-empty `contract_checking_email` + `file`; if missing, state still advances to `contract` with no notification (silent).
  - Manager-signature image is a hard-coded absolute external URL; if backend host is unreachable at mPDF render time the signed contract PDF renders without the signature image (Legal/Gov, External Integration).
  - `insertState` raw INSERT rethrows on failure and logs to Telegram, but the preceding `set('moderation_state')` in-memory change may already be staged before `save()` completes (Idempotence).
  - Country gate: `listContract` only builds a create form for `cz` (and `ro` when `contract_additional_data_form` enabled); other tenants (md) get no form here (Multi-tenant).
