## B. Behavior Digest
- Trigger: Admin opens `/admin/contact/remove_duplicates`. Two GET modes on the same route/controller: (a) `?skipPhone/skipRc/skipEmail=` → adds a value to the `skip_contact_duplicates` Drupal state list and redirects (`display()`:22-38, `filterRows()`:254-270); (b) `?id=<contactId>` → the **destructive merge** path, elects that contact id as the survivor ("Hlavní účet") and merges all duplicates in the current group into it (`display()`:81, 146-148 → `removeDuplicates()`:153).
- Preconditions:
  - Actor holds `edit contact entities` (`contact.routing.yml:38-39`). Note: this is the *same* low permission used for ordinary contact editing — no dedicated "merge/delete contacts" permission gates the destructive action (`Data Loss`, `Security`).
  - The chosen survivor `id` must appear in `$this->ids` for the group currently rendered by `display()` (`removeDuplicates()`:157-160); otherwise "Internal error" + redirect. `$this->ids` is only populated by the group-building code that runs earlier in the *same* `display()` call (`display()`:93-94), i.e. the first duplicate group returned by `reset($arr)` (`display()`:83-84). `Hypothesis`: because only the first group is materialised, a survivor id from any other duplicate group fails the membership check — merge is effectively limited to the first-listed group per request.
- Main Steps (ordered):
  1. Detect duplicate groups by three raw grouped SQL queries over `contact`: same `rc`, same `phone`, same `email`, each `HAVING count(distinct id) > 1` (`display()`:40-76). Results filtered against the skip-list (`filterRows()`:254-270).
  2. Take the **first** duplicate group (`reset($arr)`, `reset($data)`) (`display()`:83-84) and expand it transitively via `findSimilarContacts()` — recursive raw SQL `OR` over phone/email/rc until the closure of linked contacts stops growing (`findSimilarContacts()`:370-414). Result stored in `$this->ids`.
  3. Render a table of the group for the admin (created date, name, rc, blacklist string, leads, "user exists" flag, per-row "Hlavní účet" button linking back with `?id=`) (`display()`:97-145). Purely presentational.
  4. When `?id=` present, call `removeDuplicates($id)` (`display()`:146-148). Validate survivor ∈ `$this->ids` (`removeDuplicates()`:157-160).
  5. For every other contact id in `$this->ids`, load it and `replaceDuplicates($dupEntity, $survivorId)` (`removeDuplicates()`:161-166).
  6. `replaceDuplicates()` (`:280-288`) reparents references then **deletes the duplicate ContactEntity**:
     - `replaceApplications()` (`:290-317`): reassigns `application.lead_contact`, `application.child` to survivor; for `fundraiser`/`patron` roles, resolves the linked contact via `users_field_data` and rewrites `contact` on the fundraiser/patron object; each via `ApplicationEntity->save()` / linked-entity `->save()`.
     - `replaceAprofiles()` (`:319-340`): rewrites `aprofile.fundraiser` / `aprofile.patron` / `aprofile.child` to survivor via `ApplicationProfileEntity->save()`.
     - `replaceUsers()` (`:342-368`): finds the `users_field_data.contact = dup` user, reassigns `application.fundraiser` / `application.patron` from that user, then **`User->delete()`** removes the user account tied to the duplicate contact.
     - `$contactEntity->delete()` (`:287`): removes the duplicate contact (and its `contact_revision` / `contact_field_revision` history — entity is revisionable, `db-models.md:369`).
  7. Collect touched application ids into static `$applicationIds`, render a success message with links, redirect back to the route (`removeDuplicates()`:167-181).
- Postconditions: All Applications / aprofiles / (indirectly) users that pointed at the merged duplicate contacts now point at the survivor contact; duplicate `contact` rows and their revisions are deleted; the User accounts owning duplicate contacts are deleted. Elasticsearch re-index queued for each saved application (see Side Effects).
- Side Effects (cascade via `ApplicationEntity->save()` inside the merge loop):
  - `ApplicationEntity::postSave()` runs for every reparented application (`application/src/Entity/ApplicationEntity.php:197-226`): enqueues the application for Elasticsearch upload (`patron_base.default->addToQueue('application', id, 'es_upload_queue')`, `PatronBaseService.php:416-426`); dispatches `ApplicationStatusUpdateEvent` (`ApplicationEntity.php:202,228-231`) — consumed by notification, application_reaction, and scoring subscribers (`notification/…/ApplicationStatusUpdateSubscriber.php`, `application_reaction/…`, `scoring/…`); runs campaign status/category sync and may emit a Telegram alert on campaign/application status mismatch (`ApplicationEntity.php:206-219`).
  - `ApplicationEntity::preSave()` (`:159-192`) may mutate flags/changed-time and, on some state combinations, call `removePatron()` — invoked incidentally by any triggered save.
  - Net: a routine data-hygiene merge can fan out into notification e-mails, reaction recomputation, scoring, campaign sync, and ES re-index for each affected application. `Hypothesis` on exact notification content (depends on each subscriber's state gating) — the *dispatch* is Confirmed.
- Integration Calls: Elasticsearch upload queue (`es_upload_queue`) per saved application; Telegram logger only on campaign-sync mismatch / queue-insert failure (`ApplicationEntity.php:217`, `PatronBaseService.php:424`). No direct external HTTP inside the dedup controller itself.
- Failure Modes:
  - **No DB transaction / no dry-run** (`Data Loss`): the whole multi-entity rewrite + deletes in `removeDuplicates()`/`replaceDuplicates()` (`:153-368`) runs with **no** `Database::startTransaction()`, no `rollBack`, no preview. A PHP error, timeout, or a failing `save()` mid-loop leaves a **partially merged** graph — some references reparented, others not, and possibly a contact/user already deleted — with no rollback. Confirmed (grep for transaction/dry-run in controller: none).
  - **Irreversible user deletion**: `User->delete()` (`replaceUsers()`:365-367) hard-deletes the account of any duplicate contact; standard Drupal user cancel/anonymise flow is bypassed. Confirmed. `Legal/Gov` (GDPR — deleting a data subject's account as a side effect of merge, no audit of consent).
  - **Contact revision history lost**: duplicate `ContactEntity->delete()` (`:287`) drops its revision rows; the survivor does **not** absorb the duplicate's field history — merge is destructive, not archival. Confirmed (`Data Loss`).
  - **Non-idempotent re-index / event storms** (`Idempotence`, `Async`): re-running the merge or the fan-out saves can re-enqueue ES items (guarded by a `LIKE` dedup check in `addToQueue`, `PatronBaseService.php:417`) and re-dispatch status events; the status event has no "merge" awareness, so notifications may fire for unchanged states. `Hypothesis` on notification suppression.
  - **Survivor-scoping edge**: only the first duplicate group is materialised into `$this->ids` per request (`display()`:83-93); a survivor id from another group → "Internal error" (`removeDuplicates()`:157-159). `Partial`.
  - **Recursion / performance**: `findSimilarContacts()` (`:370-414`) recurses with raw `OR` queries and `array_unique`/`rsort` closure until fixpoint; on large duplicate clusters this can be expensive and, if data changes between iterations, could loop longer than expected. `Hypothesis`.
  - **No multi-tenant / country guard** (`Multi-tenant`): duplicate detection groups purely by `rc`/`phone`/`email` across the whole `contact` table (`display()`:40-76) with **no** country (CZ/RO/MD) or field_name/type predicate; contacts from different countries or different roles sharing a phone/email can be grouped and merged. Contact carries no explicit country column (`db-models.md:369-393`), so cross-country collision is possible. `Partial`.
- Note (Conflict vs START hint): START hint said "ContactEntity dedup logic; raw SQL merge". Correction: the *dedup + merge orchestration lives entirely in the controller* (`ContactRemoveDuplicatesController`), not in `ContactEntity`. `ContactEntity::preSave()` (`ContactEntity.php:134-154`) only sets the revision author; it has **no** custom `delete`/`postDelete`/merge hook, and `contact.module` defines **no** entity-delete hook. The "raw SQL WITHOUT transaction/dry-run → Data Loss" characterization is Confirmed, but the raw SQL is *read/reparent* SQL in the controller plus entity `save()`/`delete()` calls — not a single raw SQL merge statement.

## C. Data Footprint
- Entities Written:
  - `contact` — duplicate rows **DELETED** (`ContactEntity->delete()`, `:287`); revisions dropped.
  - `application` — `lead_contact`, `child`, `fundraiser`, `patron` reassigned via `ApplicationEntity->save()` (`:294-316,351-363`); each save cascades postSave.
  - `aprofile` — `fundraiser`/`patron`/`child` reassigned via `ApplicationProfileEntity->save()` (`:324-338`); also the contact linked from fundraiser/patron objects rewritten (`:307-315`).
  - `users_field_data` / user — user owning a duplicate contact **DELETED** (`User->delete()`, `:365-367`).
  - `queue` (`es_upload_queue`) — items created per saved application (`PatronBaseService.php:421-422`).
  - `application_states` — possibly a `new`-state row inserted by postSave for applications in state `new` (`ApplicationEntity.php:222-225`). `Hypothesis` (only if condition met).
  - Drupal `state` `skip_contact_duplicates` — written on the skip path (`display()`:36).
- Entities Read: `contact` (grouped dedup + `findSimilarContacts` raw SQL, `:40-76,382-405`); `application` (role lookups, `getApplications()`:187-197, raw SQL by role); `aprofile` (`getAprofiles()`:199-202, raw SQL); `users_field_data` (`getUserId()`:276-278); application status vocabulary (`\Drupal::service('application')->getApplicationModStats()`, `:220`); `queue` (dedup check, `PatronBaseService.php:417`).
- Constraints involved: `contact` has **no unique** constraint on rc/phone/email (phone unique=NO; only composite *index* `contact_email_phone_field_name_type`, `db-models.md:393`) — which is *why* duplicates exist and why this manual merge is needed. - Multi-tenant scope assumptions: **None enforced.** Dedup queries and merge span the entire `contact` table with no CZ/RO/MD or role scoping (`display()`:40-76). Cross-country / cross-role merges are technically reachable. `Partial`.
