**Discipline:** section (a) = **DB-level / storage** constraints. Section (b) = **application-level** validation. They are kept strictly separate. Only `confirmed:true` validation signals are stated as fact; anything unproven is `Hypothesis:` with `Missing evidence:`.

**Framework caveat (applies throughout §a):** ~35 of the 37 custom entities have **no `hook_schema()`**; Drupal auto-generates their SQL schema from `baseFieldDefinitions()`. So implicit primary keys (`id` serial), `uuid` unique keys, and entity-reference `*_target_id` columns are **framework conventions**, not source-declared constraints. `setRequired(TRUE)` is a **validation/form-level** required flag, **not** a guaranteed DB `NOT NULL`. Drupal entity_reference does **not** create real DB foreign keys.

### a.3 Entity-reference "FK-like" relations (NOT enforced DB FKs)

All `entity_reference`/`file`/`image` base fields create `*_target_id` columns but Drupal does **not** create DB-level foreign keys. Full per-entity relation list is in [db-models.md](db-models.md). Domain-critical soft references (all Verified `Confirmed` for the 8 verified entities): application→{user×6, contact×2, aprofile×2, organisation, taxonomy_term, campaign, contract×4, file×2}; campaign→{user×3, campaign(self), patron, taxonomy_term, kraj}; contact→{user×2, taxonomy_term, user_note, self-revision}; contract→{user×2, file×4, self-revision}; transaction→{user, campaign×2, transaction(self)}; voucher→{user, campaign, transaction}. Self-references: campaign.parent→campaign, transaction.parent→transaction.

### a.4 Revision relationships (FK-like, framework-generated)

Revisionable entities link base→revision tables via the `vid` revision key: `application`→application_revision/_field_revision; `application_reaction`→application_reaction_revision/_field_revision; `contact`→contact_revision/_field_revision; `contract`→contract_revision/_field_revision; `contract_template`→contract_template_revision/_field_revision; `user_note`→user_note_revision/_field_revision.

## (c) Hypotheses & missing evidence

- **`Hypothesis:` Most entity NOT NULL / index / unique / FK constraints are NOT source-declared.** With no `hook_schema()` for ~35 entities, physical DDL is Drupal-generated. `Missing evidence:` a live/last-installed schema dump (none in scrubbed intake; static pass — see [../tasks/Runtime-truth-policy.md](../tasks/Runtime-truth-policy.md)).
- **`Uncertain:` `organisation__worker` composite index + `is_admin NOT NULL`.** Declared in `WorkerEntityReferenceItemFieldType::schema()` but the organisation verdict (`constraints_confirmed=false`, confidence Partial) could not re-open that file within its allowed scope. `Missing evidence:` re-verification of [WorkerEntityReferenceItemFieldType.php](../../intake/current-solution/_source/patronus/web/modules/custom/organisation/src/Plugin/Field/FieldType/WorkerEntityReferenceItemFieldType.php).
- **`Hypothesis:` `maib_example` table is unused scaffolding.** `Missing evidence:` any runtime reference / write path in the maib module.
- **`Conflict — requires clarification:` dangling entity_keys / commented-out fields** — application (moderation_state, status not in baseFieldDefinitions), application_log (label→name, status), campaign_log (label/status), email (body2), application_reaction (action), scoring_entity (label→name, status), blacklist (gift_name/list_type stale display; status), snapshot_entity (status), contract_template (status), transaction_mails (label→name vs subject). None resolved; recorded per entity in db-models.md.
- **`Conflict:` config-vs-annotation translation.** campaign, application_action, email, feedback, costs_entity, snapshot_entity, contract, kraj/obec/okres/psc carry `language.content_settings.*` and/or per-field `setTranslatable(TRUE)` while their annotation declares no `data_table`/`translatable`. Effective translation behavior not verifiable statically.
- **`Hypothesis:` custom field-type storage internals** for `rc`, `eligible_email`, `country_phone`, `campaign_entity_reference` (weight item), `worker_entity_reference` (is_admin) not fully expanded. `Missing evidence:` full read of each FieldType plugin `schema()`/`propertyDefinitions()`.
- **`Hypothesis:` no TTL/expiry constraints declared.** voucher (expiration/reminded/applied), transaction_recurring (token_expiration_date), application_session lifecycle are handled in application logic (cron/services), **not** as schema constraints. `Missing evidence:` none needed — confirmed absent from schema; behavior lives in code.
- **Permissive external validators (behavior, not constraint):** `email::validateDomain` (returns true on API error/403/AVAILABLE) and `scoring::isIcoValid` (permissive when ARES down) can pass invalid values — noted so downstream agents don't treat them as hard gates.
