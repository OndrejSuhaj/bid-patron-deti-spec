## OQ-01 — `/zadost/zadatel` vs `/zadost-formular` — **RESOLVED: Confirmed, single flow (not a conflict)**

**Original verdict (UI-only):** Conflict — two apparently divergent application-entry URLs, relationship
unresolvable from screenshots alone.

**Code verdict: Confirmed — these are two sequential steps of the SAME application-intake flow
(UC0001.1), not two competing UCs.** No duplicate UC should be minted; UC0001 already models the
mechanism found in code (see "UC alignment" below).

### Route/controller evidence

1. **Role-choice landing page** (screenshot audit could not locate its URL; code shows it is the page
   carrying the "I want to help my child" / "I want to help a child I know" cards):
   `web/themes/custom/patron_cz/templates/views/views-view--supporter-zone.html.twig:162-179` — two
   hard-coded links:
   - `<a href="/zadost/zadatel">` → "I want to help my child" (fundraiser/žadatel role) — "Fill out the
     application".
   - `<a href="/zadost/patron">` → "I want to help a child I know" (patron role).

2. **`/zadost/zadatel` is the contact/consent gate**, and it is a path alias for the Drupal route
   `application.user.create`:
   `web/modules/custom/application/application.routing.yml:227-236`
   ```yaml
   application.user.create:
     path: "/application/start/{role<fill|apply>}" # fill - fundraiser, apply - patron
     defaults:
       _form: '\Drupal\application\Form\UserCreateForm'
     requirements:
       _user_is_logged_in: 'FALSE'
   ```
   `role=fill` → aliased as `/zadost/zadatel` (fundraiser); `role=apply` → aliased as `/zadost/patron`
   (patron). The role-string mapping (`fill`→`fundraiser`, `apply`→`patron`) is in
   `UserCreateForm::getRole()` (`web/modules/custom/application/src/Form/UserCreateForm.php:226-234`)
   and duplicated in `ApplicationHelperController::getRole()`
   (`web/modules/custom/application/src/Controller/ApplicationHelperController.php:118-124`).

3. **`UserCreateForm`** (`web/modules/custom/application/src/Form/UserCreateForm.php`) is exactly the
   screen the UI audit recorded at `/zadost/zadatel` (§6 of `ui-observed-areas.md`): only e-mail
   (`buildForm` line 110-116), phone (line 117-129), and (CZ-only) one GDPR consent checkbox
   `gdpr_cz` (line 130-138) — verbatim matches the screenshot's "Souhlasím se zpracováním osobních
   údajů a informováním o projektu." On submit (`submitForm`, lines 197-215):
   - looks up an existing User by e-mail; if none exists, calls `accountService->ensureUser(...)` and
     **creates the Application entity stub** (`createApplication()`, lines 245-256) with
     `moderation_state='new'`, `state='new'`, `lead_source='zone'`, `lead_role=<role>`.
   - redirects (after sending the activation e-mail) via `route_name = 'application.application.' .
     $role` — i.e. straight into the multi-step wizard route.
   - if the e-mail already belongs to an existing User, the destination is `/account` instead (no new
     Application stub) — the activation e-mail is still sent.

4. **`/zadost-formular` is the 5-step wizard**, and is a path alias for the entity-form route that
   `UserCreateForm` redirects into for the `fundraiser` role:
   `web/modules/custom/application/application.routing.yml:196-210`
   ```yaml
   application.application.fundraiser:
     path: "/application/{application}/form/fundraiser"
     defaults:
       _entity_form: aprofile.application_fundraiser
     requirements:
       _application_role: fundraiser
   ```
   The form class behind it, `ApplicationProfileFundraiserEntityForm`
   (`web/modules/custom/application/src/Form/ApplicationProfileFundraiserEntityForm.php`), extends
   `ApplicationProfileBaseEntityForm`
   (`web/modules/custom/application/src/Form/ApplicationProfileBaseEntityForm.php`), which implements
   the generic **multi-step (`step_fields`) wizard mechanic** (`stepFields()`, `next()`, `previous()`
   at lines 273-311). `ApplicationProfileFundraiserEntityForm::buildForm()` branches on
   `$form_state->get('step')` for steps 1-5 (lines 57-208), matching the observed stepper exactly:
   - step 1: child/story fields + `other_organisation` (parallel-collection flag) +
     `non_czech_child` flag — matches screenshot §3 "Váš příběh".
   - step 2: `gift_subcategory` (taxonomy-driven), `gift_price`, school/vendor contact fields,
     attachment widgets — matches screenshot §4 "Dar, kterým vám pomůžeme" (gift-category picker).
   - step 3: `fundraiser_double_address`, `employed_status`, `receiving_social_benefits`,
     `non_czech_child`-conditional `type_of_residence_permit` — matches screenshot §5 "Údaje o vás".
   - step 4: `patron_*` fields (defaults pulled from the linked patron ApplicationProfile) — the
     uncaptured "Patron" step.
   - step 5: `attachments_residence_permit`, `attachments_employment_registration`,
     `unemployment_reason`, `traffic_source` — the uncaptured "Přílohy" step.

5. **The "Zpět na výběr" back-link** observed on `/zadost/zadatel` (§6) is explained by two consistent
   code sources:
   - The dedicated Twig template for `UserCreateForm` itself,
     `web/themes/custom/patron_cz/templates/form/form--application-user-create.html.twig:9-12`,
     renders a "Back to selection" link (`'Back to selection'|t`) pointing at
     `current_item_path == 'fill' ? '/zadost/zadatel' : '/zadost/patron'` — i.e. **the role-choice
     page itself** is one hop away; the template computes the sibling role's URL as the "back" target.
   - The reusable Gutenberg header block used on "application related pages"
     (`web/modules/custom/patron_gutenberg_cz/blocks/application_header/block.json:43-50`) has example
     content literally captioned `"link": "Zpět na výběr"` with the header explicitly described as
     "Header for application related pages" — confirming "Zpět na výběr" is a **standard pattern
     across the application intake screens**, not a one-off.
   - The **prior selection step** that "Zpět na výběr" returns to is the role-choice landing shown in
     `views-view--supporter-zone.html.twig` (evidence item 1 above): "Do you know of a child who needs
     help?" with the two role cards. (Its own URL — e.g. `/zadost` or `/pozadat-o-pomoc` — was not
     directly confirmed by an exported code artifact; see Residual gap below.)

### Verdict and UC alignment

`/zadost/zadatel` and `/zadost-formular` are **not** two competing/legacy application-entry flows.
They are consecutive steps of **one** flow:

```
role-choice page  →  /zadost/zadatel (UserCreateForm: email+phone+consent)
                       │
                       ├─ new user/application → activation e-mail → redirect to
                       │  /zadost-formular (application.application.fundraiser,
                       │  the 5-step ApplicationProfileFundraiserEntityForm wizard)
                       │
                       └─ existing user → activation e-mail → redirect to /account
```

This **matches `UC0001.1` (Customer self-registration) exactly as already drafted** in
`_ar/spec-draft/UC/UC0001_SubmitApplication.md`:
- UC0001.1 step 1 ("Customer: opens the registration entry point, selecting the fundraiser or patron
  role") = the role-choice landing page.
- UC0001.1 step 2 ("System: presents a minimal registration form (email, phone, and country-specific
  consent/regulatory checkboxes)") = `/zadost/zadatel` / `UserCreateForm`.
- UC0001.1 steps 6-9 (User/Contact/Application/ApplicationSession creation) = `ensureUser()` +
  `createApplication()` in `UserCreateForm::submitForm()`.
- UC0001.1 step 11 ("...directing a new Customer to continue the Application form...") = the redirect
  to `application.application.fundraiser` (`/zadost-formular`), i.e. the 5-step wizard.

**No new UC or UC0001 alternative-flow branch is required.** UC0001 already describes this correctly
at the current level of abstraction; the only value-add from this evidence pass is the concrete
route/URL mapping and the confirmation that both paths are current (no deprecation markers,
redirects-to-nowhere, or dead code found in either route).

### Residual gap (not code-resolvable from this pass)

- The **exact URL of the role-choice landing page** itself (`/zadost` vs `/pozadat-o-pomoc` vs a node
  path) was not pinned down by an exported code/config artifact — `views-view--supporter-zone.html.twig`
  hard-codes the *outgoing* links (`/zadost/zadatel`, `/zadost/patron`) but the *view's own* path alias
  is not present in the scrubbed repo (Drupal path aliases are content, not exported config, in this
  intake). Two menu links point at candidate landing pages — `'Chci přihlásit příběh' => '/zadost'`
  (`web/modules/custom/patron_base/patron_base.module:461`) and `'Požádat o pomoc' =>
  '/pozadat-o-pomoc'` (`patron_base.module:476`) — both plausibly resolve to the same or equivalent
  role-choice view, but which one (or whether both alias to the same view) is **Uncertain** from
  static source alone. Low priority: does not affect the OQ-01 conflict resolution above, since the
  wizard-entry mechanism is confirmed regardless of the landing page's own URL.

## OQ-02 — DMS SMS donation channel ("DMS TRV PATRONDETI 90/290 → 87 777") — **RESOLVED: Not integrated (Confirmed absence)**

**Original verdict (UI-only):** Uncertain — single editorial/blog mention, no ES/UC/MSG owns it.

**Code verdict: Confirmed — no DMS/SMS donation aggregator, short-code handler, or SMS payment channel
exists anywhere in the Patronus custom code.** Recorded per OQ-02's own resolution instructions as an
**externally-operated channel not integrated into Patronus**.

### Search performed

- `grep -rli` for `DMS`, `SMS` (case-insensitive), `87777`/`87 777`, "short code", "smsbrana",
  "sms_service", "sms gateway" across all custom modules (`web/modules/custom/**/*.php`, `*.module`,
  `*.yml`). Six files matched a bare `sms` substring; each was inspected individually:

  | File | What it actually is |
  |---|---|
  | `web/modules/custom/application_log/src/Form/ApplicationActivityForm.php:31` | `'sms' => $this->t('SMS')` — one option in a staff **activity-log communication-channel** select (`call` / `email` / `sms`), used to record how staff contacted an applicant. Not a donation channel. |
  | `web/modules/custom/application/src/Entity/ApplicationEntity.php:797-801` | Same `call`/`email`/`sms` enum, as an `activity` base field on the Application entity — again a contact-log channel, not payment. |
  | `web/modules/custom/netopia/src/Mobilpay/Payment/Request/Sms.php` | A vendored class from the **Netopia/mobilpay.ro** Romanian payment-gateway SDK implementing `Mobilpay_Payment_Request_Sms` (a premium-SMS *payment type* the SDK supports in general). |
  | `web/modules/custom/netopia/src/Mobilpay/Payment/Request/Abstract.php`, `Notify.php` | Same SDK; generic request/notify base classes, not SMS-specific. |
  | `web/modules/custom/netopia/src/Mobilpay/Payment/Request.php:15,35,112` | Defines `const PAYMENT_TYPE_SMS = 0x01` and `const PAYMENT_TYPE_CARD = 0x02`, with `PAYMENT_TYPE_SMS` as the class's **unused default** (`$m_type = self::PAYMENT_TYPE_SMS` at construction, only overridden when a real request type is set). |
  | `web/modules/custom/netopia/src/Commands/NetopiaCommands.php` | Drush command scaffolding; no SMS-specific dispatch logic found. |

- `Mobilpay_Payment_Request_Sms` is **never instantiated** anywhere in `web/modules/custom/netopia/`
  (confirmed by `grep -rln "Mobilpay_Payment_Request_Sms\|PAYMENT_TYPE_SMS"` — the only other hit is the
  constant declaration/default in `Request.php`, not a call site). The live Netopia/mobilpay
  integration (used for RO card payments, per ES-synthesis) exercises `PAYMENT_TYPE_CARD`, not SMS.
- No config entities, REST resources, queue workers, or cron jobs reference an SMS aggregator, DMS
  provider, or a short-code/keyword table (`grep` for "DMS", "87777", "short code" returned zero hits
  across the whole custom-code tree).
- No `sync_config/` or `config/` YAML defines an SMS-gateway service, webhook endpoint, or
  premium-SMS product.

### Verdict

**Confirmed absence.** The "DMS TRV PATRONDETI 90/290 → 87 777" channel referenced in the one blog
article (`_ar/evidence/ui/ui-observed-areas.md` §15) is **not represented in Patronus code in any
form** — no aggregator client, no webhook receiver, no reconciliation hook. This is consistent with
the ES-synthesis note ("SMS — no dedicated gateway — likely none)" cited in the open question. Per
OQ-02's own resolution path, this closes as: **an externally-operated donation channel whose proceeds
(if any) would arrive as an unattributed bank credit and be handled by the existing bank-reconciliation
mechanism (UC0008), not as a dedicated Patronus-integrated payment channel.** No new ES/UC/MSG should
be promoted for this.

## OQ-05 — Group / collection-account story type — **RESOLVED: Confirmed, no distinct type/bundle in code**

**Original verdict (UI-only):** Partial — entity-model gap; homepage shows a distinct
"SBÍRKOVÝ ÚČET" / "Nechám to na vás" card type, glossary/EN0004 story-type enum has no explicit
collection-account/group value.

**Code verdict: Confirmed — the Campaign entity has exactly one `type` field with four allowed values;
there is no fifth "group"/"collection-account" value and no separate Campaign bundle for it.** This
corroborates (does not overturn) the `Partial` flag already recorded in `DOMAIN-kernel.md` line 49 and
glossary `C004`.

### Evidence

1. **Single Campaign bundle.** Only one config file matches a campaign entity-bundle pattern:
   `config/core.entity_form_display.campaign.campaign.default.yml` (bundle = `campaign`); no
   `core.entity_form_display.campaign.<other-bundle>.*.yml` exists. Confirms Campaign is
   **not** a multi-bundle entity type in this Drupal instance.

2. **`type` field definition** — the full and only enumeration, in
   `web/modules/custom/campaign/src/Entity/CampaignEntity.php:825-838`:
   ```php
   $fields['type'] = BaseFieldDefinition::create('list_string')
     ->setLabel(t('Typ příběhu'))
     ->setRequired(TRUE)
     ->setDefaultValue('basic')
     ->setSettings([
       'allowed_values' => [
         'basic'      => t('Obyčejný příběh'),
         'promo'      => t('Promo příběh'),                    // 4/6pos
         'long_term'  => t('Sloučený příběh dlouhodobý'),
         'short_term' => t('Sloučený příběh krátkodobý'),
       ]
     ])
   ```
   This matches glossary `C004` exactly (basic / promo / long-term / short-term) — **no "group" or
   "collection-account" value is declared anywhere** (`grep -n "'group'\|collection_account\|sbirkov"`
   across `web/modules/custom/campaign/` returned no hits).

3. **The one true "collective" campaign is a single hardcoded record, not a type.** `isGeneral()`
   (`CampaignEntity.php:1550-1552`) identifies the **transparent/collection account** campaign by
   **numeric ID equality** against a settings value, not by `type`:
   ```php
   public function isGeneral(): bool {
     return $this->id() == Settings::get('transparent_account', 1);
   }
   ```
   This is used at the payment-result stage (`NetopiaPaymentResultController.php:36`,
   `'#is_general' => $transaction->getCampaign()?->isGeneral()`) — i.e. it flags "this Transaction
   landed on the one general/transparent campaign," which is exactly the entity the DOMAIN-kernel's
   INV07 (overpayment split-off) and the "Transparent / collection account" glossary row already
   describe (`DOMAIN-kernel.md` line 58). It is a **single distinguished Campaign instance**
   (`campaign.id() == <configured id>`), not a story-type enum value applicants or admins choose per
   story.
   - Additional corroboration: `CampaignEntity.php:1193` — a query with `->condition('transparent', 0)`
     confirms a separate boolean-ish `transparent` field/flag exists on Campaign distinct from `type`,
     reinforcing that "transparent/collection account-ness" is a flag/identity property, not a `type`
     value.

4. **The "SBÍRKOVÝ ÚČET" / "Nechám to na vás" homepage card text was not found anywhere in the scrubbed
   custom backend code or theme templates** (`grep -rl "SBÍRKOV\|sbirkov\|Nechám to na vás"` across
   `web/` returned zero hits). The homepage story catalogue is rendered by a decoupled front-end
   component (`<div class="wp-block-patron-basic-cz-campaigns-cz" data-tab-active="latest"
   data-filter-status="active" ...>` in `views-view--supporter-zone.html.twig`), i.e. a JS-driven
   widget whose card copy/logic is not present in this backend-only, GDPR-scrubbed intake. This
   component almost certainly special-cases rendering when `campaign.isGeneral()` is true (the single
   transparent/collection-account campaign gets a distinct card treatment), but that client-side
   template/logic is **not evidenced** in the available source.

### Verdict

**Confirmed: no distinct "group"/"collection-account" `type` or bundle exists in the Campaign entity
model.** The "SBÍRKOVÝ ÚČET" card the UI audit observed is best explained by the **existing** `isGeneral()`
/ transparent-account mechanism (a single well-known Campaign, flagged by ID/`transparent` field, not by
`type`) receiving special presentation treatment on the (non-evidenced) front-end — **not** a fifth
`type` enum value or a new Campaign bundle. This should be recorded as an **EN0004 clarification**
(extend the existing "Transparent / collection account" description to note it is presentation-visible
as a distinct homepage card type) rather than a new story-type enum value or a new EN. Glossary `C004`
does not need a new row; a cross-reference note from `C004` to the existing "Transparent / collection
account" glossary concept (`DOMAIN-kernel.md` line 58) would suffice, left to the EN/glossary pass.

**Residual gap:** the actual front-end card-selection/labelling logic ("Nechám to na vás" CTA copy,
whether *any* `isGeneral()` campaign gets this card or only a specifically configured one) is not
evidenced in backend source — this remains a front-end/decoupled-component gap, not resolvable from
this repo. If the rebuild needs the exact card-trigger condition, it would require either the frontend
repo (not in this intake) or a runtime observation (out of scope per the static Runtime-truth-policy).
