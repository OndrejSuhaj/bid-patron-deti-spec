> **Headline current-state truth.** Patronus has **almost no real consistency boundaries today**: there

## 1. Strong-consistency zones (within-aggregate atomic intent)

Writes that a rewrite should treat as one atomic unit **and** that today at least happen within a single

must hold within the aggregate boundary.

## 3. Cross-aggregate coordination & risky patterns

The concentrations a rewrite must confront. Each cites the kernel hotspot(s), invariant(s) and flow(s).

1. **Status orchestration as an entity-save side-effect (not a service).** Every Application save
   unconditionally dispatches a status event to 3 synchronous subscribers (notification, reaction,
   scoring) which perform raw-SQL writes bypassing the entity API. No changed-state guard, no idempotence
   (re-log / re-send on unchanged re-save), no transaction isolation. *Any* of ~66 states is reachable
   from any state on 2 of 3 admin forms with no server-side legality check. **HS01, HS02**; INV14/16;
   FLW0001/0002; UC0002.

2. **Money side-effects on Transaction save + overpayment split + completion, re-entrant, from every write
   path.** The Transaction save recomputes the Campaign, splits overpayment into a child Transaction
   booked to the transparent account, promotes recurring/voucher, grants the supporter role, sends email
   + Slack, and cascades a nested Campaign save that can flip Campaign **and** Application to complete —
   from callbacks, cron and imports, with no callback idempotence and re-entrant saves risking
   recursion/extra rows. **HS03**; INV01/03/07/08/10/21; FLW0003/0006/0007.

3. **Optimistic PAID on recurring charge.** The recurring cron marks the child Transaction PAID because
   the gateway call did not throw (actual charge confirmed later async), booking unconfirmed money and
   firing thank-you email + Slack + campaign recompute. No lock/claim on the schedule; overlapping runs or
   mid-flight failure can double-charge (28-day SQL window is the only, non-atomic dedup). **HS04**; INV09;
   FLW0007.

4. **Duplicate / non-idempotent confirmations & callbacks.** The payment-identity tuple has no DB unique
   key and donation creation has no idempotency key; the callback route is effectively public with no
   HMAC (authenticity is a replayable shared secret), so concurrent/replayed callbacks can create
   duplicate Transactions or re-run side-effects. A silent no-match leaves a legitimately paid Transaction
   never marked PAID (lost reconciliation). **HS12**; INV25; FLW0003 §Failure-Modes.

5. **Overpayment split couples AG3 to AG2 funding state.** A paid Transaction that overpays its Campaign
   creates a linked child Transaction (transparent flag, parent link) to keep "raised ≤ target". The
   split guard is re-evaluated every callback after a price mutation, inside a re-entrant save. **HS03**;
   INV07; FLW0003 §Side-Effects.

6. **Contact is a shared mutable party store written cross-aggregate.** One Contact entity represents
   child/fundraiser/patron/school/employer/lead, disambiguated only by a discriminator, referenced by
   Application and ApplicationProfile via soft references with no DB FKs and **no uniqueness** on
   national-number/phone/email. The **risk classification is written by AG9** via a raw update keyed on
   email **with no LIMIT**, so all Contacts sharing an email (or with empty email) are overwritten.
   **HS08**; INV15/23; FLW0016/0023.

7. **Scoring writes three aggregates non-transactionally.** A scoring approval sets the Application to
   `scoring_ok` (AG1), creates Blacklist entries linked to that Application (AG9), and propagates the
   classification onto the matching Contact (AG7) — in one flow with no transaction. **HS08, HS10**; INV15;
   FLW0016.

8. **Destructive dedup / merge with no transaction, hard-deleting users and history.** *Contact dedup*
   (AG7) reparents all references from Application / ApplicationProfile / linked User to a survivor Contact
   then **hard-deletes** the duplicate Contact (revisions dropped) **and its owning User** (bypassing GDPR
   cancel/anonymise), with no DB transaction, rollback or dry-run — a mid-loop failure leaves a
   half-merged graph. It also fans out (per reparented Application) the full status event storm + ES
   re-index. *Lead pairing* (AG1) carries only the patron profile/User and silently overwrites a
   pre-existing patron profile (orphaning it). *Organisation dedup* (AG8) reparents only the employer
   reference, leaving other references dangling. All with no country/role scoping. **HS09**; INV17/18/19;
   FLW0023/0024/0025.

9. **Status/campaign lock-step can silently diverge.** Application ↔ Campaign status/gift-category are
   kept mutually consistent as a save side-effect; a detected desync is only **Telegram-alerted, not
   repaired** — the two aggregates can drift with no reconciliation. INV04; FLW0002/0022.

10. **Publish activates two aggregates with no transaction wrapping.** Publishing a Campaign transitions
    both Campaign (active + published stamps) and Application (active) together; a partial failure leaves
    an inconsistent pair. INV13; FLW0021.

11. **Contract signature drives a different aggregate's state; numbering is race-prone.** The two-step
    signature progression has no status on the Contract itself — the observable workflow state is on the
    Application (INV11), and the per-year contract number is app-level-unique only (MAX+1, no DB key,
    concurrency race). INV11/22; FLW0008.

12. **Synchronous messaging inside the save; anti-erasure Mautic re-upsert.** Transactional mail is sent
    synchronously in-request from entity-save paths (queue disabled), so a slow/failing Mautic call blocks
    or aborts the save; no retry; archive delivery status never tracked. GDPR anonymisation blanks in place
    yet the save re-enqueues the user to Mautic which re-creates the contact with names intact. **HS13,
    HS06**; FLW0019/0020.

13. **Reconciliation matching is fragile and lossy (multi-context cron/import → AG3).** Three legs each
    carry data-loss risk (skipped-day-on-failure with no retry; a 30-row reconcile cap leaving excess
    rows unmarked; brittle HTML parsing that blanks on template change; unstable idempotency key). **HS05**;
    FLW0011/0012/0013.

## 4. Rewrite guidance

> **This section is recommendation, not current-state fact.** Each item states the boundary a rewrite
> *should* enforce, grounded in the evidence above. Items marked **[current-state fact]** merely restate an
> observed defect; everything else is a **[recommendation]**.

| # | Risky pattern (from §3) | Recommended boundary | Grounding |
|---|---|---|---|
| 1 | Status orchestration as save side-effect | **[recommendation]** Lift the ~66-state workflow into a first-class state machine with an **authoritative, enforced transition table** (transactional state change), **idempotent** handlers, and **guarded/async** side-effects (domain events consumed out-of-band). | HS01/HS02; INV14/16; UC0002 |
| 2 | Money side-effects + split + completion on save, re-entrant | **[recommendation]** Make the Transaction PAID transition an **atomic transactional command** within AG3; publish a **domain event** for campaign recompute/completion, recurring/voucher promotion, role grant and messaging — consumed **eventually**, each idempotent. No nested re-entrant saves. | HS03; INV01/03/07/21 |
| 3 | Optimistic PAID on recurring charge | **[recommendation]** Charge under a **claim/lock** on the schedule; mark PAID only on **confirmed** settlement (treat the gateway acknowledgement as pending until confirmed); use a durable idempotency key per charge instead of the 28-day SQL window. | HS04; INV09 |
| 4 | Duplicate/non-idempotent callbacks & confirmations | **[recommendation]** Add a **DB unique constraint** on the payment-identity tuple and an **idempotency key** on donation creation; **authenticate callbacks (HMAC/signature)**; make no-match observable, not silent. **[current-state fact]** today uniqueness is app-level only and the route is effectively public. | HS12; INV25 |
| 5 | Overpayment split | **[recommendation]** Keep the split **transactional within AG3** (parent+child created atomically) and evaluate it **once** per confirmed payment, not per callback. | HS03; INV07 |
| 6 | Contact shared mutable party store | **[recommendation]** **Split party roles** (child/fundraiser/patron/employer/lead) and add **real identity/uniqueness constraints** (national-number/phone/email); never bulk-update classification by email with no scope. **[current-state fact]** one overloaded Contact, no uniqueness, raw no-LIMIT update. | HS08; INV15/23 |
| 7 | Scoring writes 3 aggregates | **[recommendation]** Make the scoring decision a **transactional command in AG9** (Blacklist + Application state), then propagate the Contact classification via an **idempotent, correctly-scoped** event (single Contact, not email-keyed). | HS08/HS10; INV15 |
| 8 | Destructive dedup/merge | **[recommendation]** Wrap every merge in a **DB transaction with rollback and a dry-run/preview**; **archive** rather than hard-delete; **never** delete a User as a merge side-effect (route through cancel/anonymise); reparent **all** references; scope by country/role; gate with a dedicated permission. **[current-state fact]** no transaction, hard-deletes User+history, single-reference reparent, no scoping. | HS09; INV17/18/19 |
| 9 | Application↔Campaign lock-step drift | **[recommendation]** Make one aggregate the **source of truth** for the shared status and derive the other via an idempotent event; **reconcile** detected desyncs, do not merely alert. **[current-state fact]** desync is Telegram-alerted, not repaired. | INV04 |
| 10 | Publish activates two aggregates | **[recommendation]** Wrap the Campaign-activate + Application-activate in **one transaction**, or split into an event with a compensating action. **[current-state fact]** no transaction wrapping (partial-failure window). | INV13 |
| 11 | Contract signature state on another aggregate; numbering race | **[recommendation]** Give the Contract its **own explicit status**; make numbering a **DB-sequence / unique-constrained** value, not MAX+1. **[current-state fact]** state is observable only on the Application; numbering is app-level-unique. | INV11/22 |
| 12 | Synchronous messaging in save; Mautic anti-erasure | **[recommendation]** Dispatch transactional mail **asynchronously via a queue with retry**, decoupled from the entity save; track delivery status on the archive; ensure erasure **actually deletes/suppresses** downstream (Mautic) and does not re-upsert. **[current-state fact]** synchronous send, dead queue worker, untracked status, anti-erasure re-upsert. | HS13/HS06 |
| 13 | Fragile reconciliation | **[recommendation]** Make each import leg **retryable and idempotent** (durable cursor instead of "yesterday"; unique constraint for dedup; robust parsing; stable idempotency key); no silently row-capped matching. **[current-state fact]** skipped-day-on-failure, a 30-row match cap leaving excess rows unmarked, brittle HTML parsing, unstable idempotency key. | HS05 |
| — | Dormant recommendation (AG7 Account) | **[recommendation]** Decide explicitly to **drop or rebuild**; do **not** treat it as live current-state behaviour. **[current-state fact]** inert on 5 grounds (INV27). | HS14; INV27 |
