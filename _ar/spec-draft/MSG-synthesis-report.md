## 1. Active rules & template used

Authored under the following normative sources (precedence: cross-layer discipline → layer rules →
template; the driving-agent task refines grouping/scope decisions only for this run):

- **`tooling/docs/rules-MSG.md`** — an MSG describes a **transactional message sent to users** and
  defines only: **when** it is sent (trigger), **who** receives it (recipients), and **what
  information** it carries (content). Recommended structure: **Purpose · Trigger · Recipients ·
  Message Content**. Frontmatter carries `doc_id / title / canonical_layer: MSG /
  spec_type: transactional-message / status`, with optional `trigger` (UC) and `references` (EN/ES).
  Forbidden content: HTML templates, email styling, mail-provider configuration (and, per the driving
  task and cross-layer discipline, SMTP/framework config, file paths, class/method names, routes,
  library names, and other delivery mechanics).
- **`tooling/docs/cross-layer-discipline.md`** — single-source ownership: **MSG owns the
  transactional-message contract** (trigger, recipients, content). It **references** UC (trigger) and
  EN (subject) — and, in this project, ES (delivery channel) — by `doc_id`, and **never restates**
  entity attributes (→ EN) or rule content (→ BR). The >50-character restatement rule applies.
- **`tooling/templates/template-MSG.md`** — the per-file skeleton used for all 30 MSG files
  (Purpose · Trigger · Recipients · Message Content, extended with Boundary/Notes and an explicit
  Evidence Level where a message carries uncertainty).

Key grouping / scope rules applied this run (from the driving task):

- **One MSG = one distinct message *type*, not one Notification-Matrix row.** The Recipients section
  of each file captures the role × channel variants (Parent/Žadatel, Patron, Donor, Coordinator/
  checking address × email / in-zone). The ~117 matrix rows are **not** exploded into ~117 files.
- **Channels:** email = **ES0006** (Mautic); *in-zone* notification = the internal party-zone
  display (Parent/Patron/Donor Zone), which is internal and **not** an ES.
- **Ops alerting is not MSG.** Slack (**ES0015**) and Telegram (**ES0016**) carry operational
  error/health alerts, not user-facing transactional messages, and are excluded from this layer.
- **Named integrations and status vocabulary** (Mautic, ComGate, Netopia, MAIB; PAID / PENDING /
  CANCELLED; `waiting_for_patron`, `scoring_ok`, `canceled_timeout`, Dobrošek, aviz, …) are allowed
  literals per the glossary and status model.
- **Current-state only** — the target assignment (`it-zadani`) is out of scope; where the current
  Notification-Matrix (code-backed `application_reaction`) and a scenario narrative disagree, the
  matrix wins for current state and the conflict is recorded in-file (see §4/MSG0013).

Cross-cutting observations, current-state:

- **Two engines produce most user messages.** The **status fan-out** (UC0002 / FN0002 → the
  configured `ApplicationReaction`, EN0026) drives the entire application/story lifecycle surface via
  a single email template family (`zone_main_template`) and the internal in-zone channel; the
  **payment/domain callbacks** (UC0006/UC0007/UC0009/UC0010, FN0007/FN0010/FN0011/FN0013) each send
  their own dedicated donor/buyer message inside the transaction/document save. Everything ultimately
  emits through **FN0019** dispatch to **ES0006** (Mautic) for email.
- **Regionalisation at the message boundary** mirrors the ES layer: several messages are CZ-only or
  behave differently per country because of the **per-country template id map** — MSG0023 (recurring
  dunning) is RO-only, MSG0028 (tax confirmation) is CZ-only (RO/MD send nothing), and MSG0003 (MD
  activation) / MSG0014 (CZ success templates) are Uncertain/Partial due to unmapped or
  commented-out template ids.
- **Channel duality is pervasive.** Most lifecycle statuses fire **both** an email (MSG0005 /
  dedicated MSG) **and** an in-zone message (MSG0006); some statuses are in-zone-only (email=NO, e.g.
  `scoring_ok` → MSG0012, `active` → MSG0013). The Notification-Matrix channel flags are the
  authoritative per-status × role split.

## 4. Messages kept broader than expected & why

- **MSG0005 (Status-Change Email) and MSG0006 (In-Zone Status Notification)** — the deliberate
  catch-alls. The Notification Matrix has ~117 rows, but they are role × status × channel variants of
  the **same** fan-out engine (UC0002 / FN0002 over the configured `ApplicationReaction`, EN0026),
  carried by one email template family and one in-zone channel. Exploding them into ~117 files would
  restate configuration data as message contracts and violate the "one message *type*" grouping rule.
  Every email-enabled status not broken out for a higher-salience intent is folded into MSG0005; the
  in-zone counterpart is MSG0006. This is a chosen breadth, not missing detail.
- **MSG0007 (Completion Reminder 1st/2nd)** — groups the Patron, Parent/fundraiser, generic, and
  return-for-completion (`waiting_reminder_*`) reminder statuses into one escalating type rather than
  a file per reminder status × role.
- **MSG0008 (Find-New-Patron)** — groups `returned_new_patron` + its two reminder statuses (whether
  reached by Patron timeout or by an explicit Patron "Decline"), because they are one
  find-a-new-Patron intent with escalation.
- **MSG0015 (Collection Unfulfilled/Partial)** — groups `campaign_uncompleted`, `uncompleted`,
  `completed_partly`, and `campaign_uncompleted_inprocess`: one "target not (fully) reached →
  coordinator decision / redistribution" intent spanning the dedicated `campaign_uncompleted` email
  and the status fan-out.
- **MSG0017 (Cancelled-Timeout)** — groups `canceled_timeout` + `canceled_fundraiser` as one
  auto/timeout cancellation type, kept distinct from voluntary (MSG0018) and story (MSG0016)
  cancellation.
- **MSG0021 (Donation Cancelled)** — groups one-time PENDING→CANCELLED and donor-initiated recurring
  cancellation confirmation, both being "your payment was cancelled, nothing charged" to the Donor.
- **MSG0027 (Contract for Signature & Signature Confirmation)** — groups `waiting_signature`
  delivery (legacy email path and the in-zone digital-signing session), the two signing reminders,
  and the `contract_signed` confirmation into one signature-lifecycle message type; the digital vs
  legacy delivery split is a channel variant, not a separate message contract.
- **MSG0029 (Feedback Request & Reminders)** — groups the feedback request, its two reminders, and
  the non-cooperative escalation as one feedback-solicitation type.

**Recorded conflict kept in-file (breadth to preserve both readings):**

- **MSG0013 (Story Published)** — the Notification Matrix marks `active` as **in-zone only**
  (email=NO for both roles) while the SC-9A narrative says "email". Per the current-vs-narrative
  rule, the code-backed `application_reaction` (matrix) wins for current state → treated as in-zone;
  the SC-9A narrative divergence is recorded as `Conflict — requires clarification` in the file
  rather than silently resolved.

## 5. Missing downstream artifacts that weaken message definition

- **BR layer not yet built (largest gap).** The **message-gating rules** that MSG currently
  *describes at trigger level* are not yet owned anywhere as canonical BR: which status × role
  combinations enable email vs in-zone; the reminder cadence (1st after ~2 days, 2nd after ~+5 days,
  timeout after ~+7 days); the 100%-of-target auto-complete threshold behind MSG0014; the "email only
  if donor supplied a matching email" condition on the bank-transfer branch of MSG0019; the
  send-once (`is_email_sent`) idempotency policy vs the **missing** guard on the uncompleted-campaign
  mail (MSG0015). MSG files currently point at UC/FN/FLW for these; once **BR** exists they should
  cite BR `doc_id`s instead of paraphrasing the cadence/threshold inline. **This is the recommended
  next step (§7).**
- **EN0026 ApplicationReaction depth.** MSG0005/MSG0006/MSG0007 depend on the `ApplicationReaction`
  configuration (status × role × channel) as the true source of the per-status enumeration. The MSG
  status lists are Notification-Matrix-evidenced, not exhaustive by construction; a fuller EN0026 (or
  a QUERY over reaction config) would let the catch-alls cite an authoritative enumeration instead of
  a "may extend beyond this list" caveat.
- **MSG0028 / EN0014 DonationConfirmation.** The RO 2%/3.5% tax-redirect variant is a distinct,
  **un-mined** path with no confirmation PDF email — flagged Uncertain and excluded pending evidence.
- **Voucher-expiry reminder (EN0013).** A `reminded` field exists but no active job is evidenced;
  excluded from MSG0024 as Uncertain until a JOB/flow confirms or denies it.
- **Template-map completeness (FN0019).** MD `activation_{role}` (MSG0003), CZ success templates for
  MSG0014, and the one-time CANCELLED / PENDING platform templates (MSG0020/MSG0021) are
  unmapped / commented-out / not surfaced in mined flows — recorded as Uncertain/Partial; a template
  inventory at the FN0019 level would firm these up.
- **CS (observed FE) layer not yet built** — would corroborate the in-zone message wording
  (MSG0006 / MSG0012 / MSG0013) that is currently reconstructed from the status vocabulary and
  Notification Matrix rather than from captured zone screenshots.

## 6. Implementation / infrastructure details excluded from canonical MSG text

Per `rules-MSG.md` restrictions and the driving task, the following are **cited to the owning
FN/EN/FLW, never restated** in MSG bodies:

- **Email/HTML templates and template ids** — `zone_main_template`, `activation_{role}`,
  `magic_link`, `thanks_for_payment` / `thanks_for_payment_transparent`,
  `thanks_for_recurring_payment`, `cancelled_recurring_payment`, `campaign_uncompleted`,
  `donation_confirmation`, `smlouvy_email_ke_kontrole`, `smlouvy_email_pro_zz`,
  `voucher_to_buyer_applied`, `campaign_successful_finish` / `zz-…` / `patron-…`. These are named
  only as delivery-layer evidence in Notes, not as message contract.
- **Mail provider / transport config** — Mautic connection, the disabled mail-queue → synchronous
  in-request/in-save send, the environment/production send-gate, SMTP/dev sinks. Owned by FN0019 /
  ES0006.
- **Framework / code mechanics** — entity `preSave` hooks, sender services/controllers, resources,
  routes (`/user/create_magic_link`, callback endpoints), CLI/cron entry points, class/method names,
  file paths, library/SDK names. Owned by UC/FN/SRV/ES + flow dossiers.
- **Send-record / idempotency mechanics** — the `is_email_sent` guard, the `reminded` field, the
  EmailArchive (EN0022) write-regardless-of-transmission behavior (archive cannot distinguish
  delivered from suppressed). Owned by EN0022 / FN0019; cited as a known evidence limitation, not a
  contract element.
- **Ops alerting** — Slack (ES0015) / Telegram (ES0016) donation/voucher/desync pings are
  operational, **not** user-facing transactional messages, and are excluded from MSG entirely.
- **Entity attributes & business-rule content** — recipient-resolution fields, amount/threshold
  computations, working-day rules, PAID-transition rules → cited to EN / (future) BR, never inlined.
