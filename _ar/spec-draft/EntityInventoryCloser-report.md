## 4. Notable findings

1. **No domain-worthy entity is un-promoted.** The one candidate that could invite debate —
   `scoring_entity` — is a defined-but-**dormant/no-writer** carrier whose live scoring data actually rides
   as JSON on the Application record; it **already holds EN0017**. So even the ambiguous case is EN-covered.
   ⇒ **No new EN promotion is recommended from this pass.**

2. **The uncovered residue is 100 % non-domain.** All 6 deferred custom types are reference (`kraj`/`obec`/
   `okres`/`psc`), a join (`supplier_to_category`), or a config-preset (`application_statuses`). This is
   exactly the long tail the inventory-closure agent is meant to leave un-expanded — deferral is correct,
   not a gap.

3. **Two confirmed-dormant subsystems surface at the entity level** (carry into any rewrite scoping):
   `account` (ML campaign-recommendation, INV27/R19 — 5 independent dormancy grounds) and `maib_example`
   (scaffolding, no runtime evidence). A rewrite should make an explicit **drop-or-rebuild** decision
   (ADR-12) rather than encode them as live behaviour.

4. **Referential integrity is entirely application-level.** No DB foreign keys exist; every cross-entity
   link is a Drupal soft `entity_reference` (target_id) or plain string/int. The only DB-level UNIQUE key
   found in custom code is `email_domain.domain`. Aggregate boundaries ([DOMAIN-aggregates.md](DOMAIN-aggregates.md))
   are therefore **logical**, not schema-enforced.

5. **The god-object and shared-store hazards are at the entity boundary:** `aprofile` (~100 fields,
   EN0002/ADR-06) and `contact` (universal party store read/written cross-aggregate, HS08/ADR-05). Both are
   fully EN-documented; flagged here as the highest rewrite-relevance entities in the long-tail review.

6. **Data-quality conflicts carried (not resolved):** dangling `label`/`status` entity_keys
   (`application_log`, `campaign_log`, `scoring_entity`, `blacklist`, `contract_template`,
   `transaction_mails`), orphaned display fields (`email.body2`, `costs_entity.type`), commented-out fields
   (`application_reaction.action`, `application_action.cron_email_id`), and annotation-vs-config translation
   mismatches. All recorded per-entity in db-models.md and referenced in the inventory Notes column.

## 6. Risks / deferred areas

- **Physical column DDL inferred, not verified.** With no `hook_schema()` for ~35 entities, exact column
  types / NOT NULL / generated indexes / unique keys are Drupal-framework-generated and not checked against
  a live/last-installed schema (static pass; [Runtime-truth-policy.md](../tasks/Runtime-truth-policy.md)).
- **Custom field-type internals partly unexpanded:** `rc`, `eligible_email`, `country_phone`,
  `worker_entity_reference` (adds `is_admin`, organisation verdict = Partial), `campaign_entity_reference`.
- **Dormant/no-writer entities** (`account`, `scoring_entity` carrier, `campaign_log` writer,
  `maib_example`, `snapshot_entity` writer) carry `Hypothesis`; not force-resolved.
- **Config-preset vs status model:** `application_statuses` (24 presets) is deferred as config; its
  relationship to `application_workflow` should be resolved during status-model reconstruction, not here.

## 8. As-is closure verdict

**Current-state entity documentation can be considered sufficiently closed as-is.**

- 100 % of Domain and Projection entities have EN docs; 86.5 % of all custom types.
- The residual long tail (6 custom types + 4 tables) is fully **named, classified, and deferral-justified**
  — reference / join / preset / infra / dormant only. Nothing domain-meaningful is missing.
- Every EN entity is placed in an aggregate (32/32, AG1–AG13).
- Zero unresolved `Uncertain` entities; zero blocked reconciliations.

from partial → covered, citing [ENTITY-coverage-matrix.md](ENTITY-coverage-matrix.md) as the substituted
coverage matrix. No further EN authoring is required for as-is closure; any expansion of the geo/join/preset
long tail into full EN pages should be an explicit, separately-scoped decision (not needed for handover).
