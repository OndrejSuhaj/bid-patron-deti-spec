An **external system (ES)** is a system that lives **outside** the Patronus platform boundary.
Internal subsystems (the SearchIndex processor, the messaging orchestrator, the reconciliation
processor, the gateway/registry adapter code, etc.) are **not** ES — only the external service is.
Same-vendor aliases are merged into **one** ES with multiple interaction modes (see Notes).

**Count: 16 external systems.** These correspond to the 17 integration-landscape boundary rows in
ARCH0001 §5 after merging ComGate's two boundaries (payment gateway + transfer/settlement sync) into
a single ES, and after folding the Facebook Conversions API + client-side Pixel + Lead Ads webhook
stub into a single Facebook ES.

## Legend & conventions

- **Direction / interaction modes** are detailed per ES file (Integration Model section). Summary:
  outbound = Patronus calls out; inbound = external system pushes/notifies; poll/pull = Patronus
  fetches on a schedule/CLI; bidirectional = outbound call + inbound callback/return.
- **Regional scope:** ComGate/Moneta/IMAP/ARES/MVČR are **CZ**; Netopia/MobilPay and Nager.Date are
  **RO**; MAIB is **MD**. The remaining systems are region-agnostic platform integrations.
- **Failure-impact / hazard tags** (`HSxx`, `INV04`, `FLWxxxx`) are owned by DOMAIN / FLOW / ARCH
  artifacts and are cited here, not restated.
- **Excluded (not external systems):** internal adapters/processors, and the composer-only Firebase
  dependency (no SDK call — Uncertain) and SMS (no dedicated gateway — likely none). See the
  synthesis report §5.
