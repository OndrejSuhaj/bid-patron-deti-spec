## 4. Consolidation decisions

**Merges (reduce fragmentation):**
- **SRV0003** absorbs `blacklist` into Scoring & Risk — blacklist is a data layer whose `blacklist_type` is *written by scoring* (`scoring_ok` auto-promotes `contact.blacklist_type`); same risk-decision boundary. `Evidence:` blacklist coupling in scoring flow (data-model-signals + integrations). *Not* derived as its own SRV (would be a passive-data-only service, prohibited by rule 8).
- **SRV0013** merges `email` + `notification` + `patron_base.APIMailingService`/`smartmailing`/MailingQueue — all share the transactional-message boundary; `notification` and `application_reaction` are event consumers that call the same mailing path. Thin duplication consolidated.
- **SRV0014** merges `facebook_leads` (CAPI + lead webhook), Facebook Pixel, `mautic`, `patron_tracking` (GTM) — one outbound marketing/analytics boundary.
- **SRV0018** merges `slack_integration` + `telegram_integration` + `elasticsearch` audit — three thin PSR-3/audit logger adapters → one Observability service.
- **SRV0009** merges `bank_integration` (IMAP) + `monetaapi` (AISP) + `accounting` reconciliation + ComGate `transferList` sync — one bank-reconciliation boundary (distinct from payment *initiation* in SRV0008).

**Splits (separate mixed concerns):**
- **SRV0001 vs SRV0002** — the application entity currently *is* both the aggregate root and the orchestrator (dispatches `ApplicationStatusUpdateEvent` from `postSave`). Split domain state from orchestration.
- **SRV0007 vs SRV0008** — payment *domain* (transaction lifecycle) split from *gateway adapters* (vendor boundaries). `TransactionEntity` currently mixes both (initiates gateway calls + side-effects in `postSave`).
- **SRV0008** keeps 3 vendor adapters (ComGate/Netopia/MAIB) as one SRV but flags each as a distinct **Vendor Lock-in** boundary (see §5) — target is a common `PaymentGateway` port with 3 adapters.

**Rejected as SRVs (no behavior evidence / passive):** `supplier_to_category`, geo entities (`kraj/obec/okres/psc`), `zip` beyond reference-data provider (folded into SRV0017), `simple_image_rotate`, `alter_entity_autocomplete` (UI utilities → belong to theme/form layer, not services).

## 6. Proposed Target SRV Structure (rewrite-ready)

Grouped by bounded context; arrows = allowed dependency direction. Target = clean ports/adapters, orchestration extracted from entities, one gateway port.

```
C1 Application & Lead
  SRV0001 ApplicationLifecycle (domain)  ──emits──▶ SRV0002 ApplicationStatusOrchestrator (orchestrator)
                                                     └─▶ triggers: SRV0013 (messaging), SRV0003 (scoring), SRV0011 (documents)
C2 Risk & Scoring
  SRV0003 Scoring&Risk (domain)  ──uses──▶ SRV0004 Identity&RegistryVerification (adapter: MVČR, ARES)
C3 Campaign & Story
  SRV0005 Campaign&StoryLifecycle (domain)   SRV0006 CampaignRecommendation (background, transitional)
C4 Donations & Payments
  SRV0007 PaymentProcessing (domain)  ──port──▶ SRV0008 PaymentGatewayAdapters (ComGate|Netopia|MAIB)
C5 Finance & Reconciliation
  SRV0009 BankReconciliation (adapter: IMAP|Moneta|Comgate transfer)   SRV0010 Reporting&Export (projection)
C6 Documents & Fulfilment
  SRV0011 DocumentGeneration&Fulfilment (domain: contract|confirmation|voucher|tax)   SRV0019 DocumentImport (OneDrive adapter)
C7 Party / CRM
  SRV0012 Party&ContactManagement (domain hub)
C8 Messaging & Marketing
  SRV0013 TransactionalMessaging (orchestrator/adapter)   SRV0014 Marketing,Analytics&Lead (adapter)
C9 Identity & Access
  SRV0015 Identity&Access (infrastructure/security)
C10 Search & Indexing
  SRV0016 SearchIndexing (background/adapter)
C11 Platform / Integration Fabric
  SRV0017 PlatformKernel&Workflow (infrastructure)   SRV0018 Observability&OpsAlerting (adapter)
```

Cross-context dependencies to enforce as explicit ports (currently implicit coupling): Application↔Campaign (state sync), Payment↔Documents (confirmation/voucher on PAID), Scoring↔Party (writes `contact.blacklist_type`), Messaging consumed by nearly every context.
