## 2. Per-aggregate detail

### AG1 — Application (Žádost / Lead) · root **EN0001**

- **Root / lifecycle anchor.** EN0001 is the heavyweight aggregate root of the domain [DOMAIN-kernel §1].
  Its single state field drives the ~66-label workflow that spans lead-era and application-era labels on
  one record — **"Lead" is the intake phase of the same Application, not a separate entity** [EN0001; INV
  §3.1; FLW0025].
- **Members** (each composed / lifecycle-dependent on the Application):
  - **EN0002 ApplicationProfile** — *composed, held ≤2 per Application* (fundraiser profile + patron
    profile, discriminated by the profile-role discriminator). Direction: Application → ApplicationProfile
    (via the fundraiser-profile / patron-profile slots). No independent lifecycle; created / filled /
    marked finished as the intake form progresses [EN0002 Lifecycle]. Cardinality bound by **INV20**. On a
    `returned_new_patron` transition the patron profile is scrubbed [EN0001 Lifecycle]; on lead merge the
    survivor absorbs the duplicate's patron profile and may silently overwrite a pre-existing one
    (**INV19**, lossy).
  - **EN0003 ApplicationSession** — *composed, fully lifecycle-dependent*. One per relevant role at
    Application creation; **all** sessions bulk-deactivated when the Application enters an
    invalidate-sessions state (**INV14**). Link is by UUID string, no reference field [EN0003 Relations].
  - **EN0025 ApplicationLog** — *composed, append-only audit child*. Every status fan-out and contract
    activity appends a row against the Application; created-only, never mutated [EN0025 Lifecycle; FLW0001;
    FLW0008]. Owned by the Application because a log row is meaningless without its Application.
- **Invariants enforced within the boundary:** INV14 (session lifecycle ⊂ Application state), INV16
  (low-risk score derived on `to_check` — reads fundraiser-profile fields, INV16 owner-coupling note),
  INV19 (lead merge reparents patron profile/User to one survivor), INV20 (≤2 profiles).
- **Command boundary (atomic within AG1):** create Application (+ initial audit row + sessions);
  set/change the Application state; fill/finish a profile; scrub patron data on `returned_new_patron`;
  deactivate sessions. **Not atomic today:** status change fans out synchronously to notification / reaction /
  scoring subscribers and cascades cross-aggregate writes (Campaign, Contract, Contact) as an
  entity-save side-effect — see CONSISTENCY-boundaries §3 and **HS01/HS02**.
- **Owning SRV:** Application-Lifecycle (create/edit) + Application-Status-Orchestrator (the status
  event/fan-out); primary **UC0001** (submit), **UC0002** (orchestrate status), **UC0016** (lead merge),
  **UC0019** (invoice import triggers status).
- **Evidence / Confidence:** EN0001, EN0002, EN0003, EN0025; INV14/16/19/20; FLW0001/0002/0010/0025.
  **Confirmed** for membership; the state machine itself is **Partial** (no legality guard, HS02).

### AG2 — Campaign (Story / Příběh) · root **EN0004**

- **Root / lifecycle anchor.** EN0004 is the public fundraising story generated from an approved
  Application; the campaign status carries the fundraising lifecycle [EN0004; DOMAIN-kernel §3.2]. 1:1 with
  its Application (a distinct aggregate — see the cross-aggregate coupling INV04, INV13).
- **Members:**
  - **EN0005 Patron (public profile)** — *composed, ≤1 per Campaign*. Referenced via the campaign's
    patron-profile slot, created/edited inline with the Campaign; no independent lifecycle [EN0005
    Lifecycle]. Cardinality
    bound by **INV20**. Distinct from the patron User/Contact of AG7 (same word, different records)
    [DOMAIN-kernel §1].
  - **EN0021 Feedback** — *composed, post-campaign child*. Fundraiser thank-you tied to a Campaign (+
    fundraiser User by reference); created from feedback forms, dispatch time stamped on send [EN0021
    Lifecycle]. Linked to the `waiting_for_feetback` Application path (that Application-side coupling is
    Partial) [EN0021 Open Q3].
  - **EN0028 CampaignLog** — *composed, append-only audit child* keyed to a Campaign [EN0028 Relations].
    **Writer not evidenced — `Hypothesis`** on who writes it (no flow dossier exercises it) [EN0028
    Lifecycle].
- **Invariants enforced within the boundary:** INV01 (raised total = SUM of paid Transaction amounts,
  recomputed on Campaign save — *the summed Transactions live in AG3*, so INV01 is a cross-aggregate
  derived total, see §3 of the consistency doc), INV03 (auto-complete when raised ≥ target), INV05
  (uncomplete after deadline when raised < target), INV13 (publish readiness gate), INV20 (≤1 Patron).
- **Command boundary (atomic within AG2):** create/generate Campaign from an approved Application;
  publish/activate (readiness gate, INV13); recompute raised + auto-complete/uncomplete; edit the Patron
  profile; append CampaignLog; author Feedback. **Not atomic today:** publish transitions Campaign **and**
  Application with no transaction wrapping (INV13 partial-failure risk); status is kept in lock-step with
  the Application bidirectionally (INV04) as a save side-effect.
- **Owning SRV:** Campaign-&-Story-Lifecycle; primary **UC0011**; participates in UC0005/UC0006 (donation
  target) and the dormant UC0021.
- **Evidence / Confidence:** EN0004, EN0005, EN0021, EN0028; INV01/03/05/13/20; FLW0021/0022/0003.
  **Confirmed** for AG2 core; CampaignLog writer **Hypothesis**; several campaign statuses
  (`suspended`/`canceled`/`completed_partly`) are **Hypothesis** (no evidenced trigger) [§3.2].

### AG3 — Transaction (Donation / Payment) · root **EN0009**

- **Root / lifecycle anchor.** EN0009 is the money record; its first transition to **PAID** is the
  money-side hub of the whole domain [DOMAIN-kernel §1; §3.3]. Multi-gateway (ComGate CZ / Netopia RO /
  MAIB MD) plus reconciliation imports that create rows already PAID.
- **Members:** none beyond **self** — an overpayment split creates a *child* Transaction (transparent
  flag, parent link → originating Transaction) within the same aggregate type (**INV07**). Transaction
  does not compose any other entity; it *promotes* RecurringTransaction (AG4) and Voucher (AG6), which are
  separate aggregates it acts on by reference [EN0009 Relations].
- **Invariants enforced within / anchored on the boundary:** INV07 (overpayment child split preserves
  "raised ≤ target"), INV25 (payment-identity uniqueness is app-level only — no DB key, no idempotency
  key). INV01/INV03/INV21/INV08/INV10 are **triggered by** a Transaction reaching PAID but land on *other*
  aggregates → they are cross-aggregate (see consistency doc).
- **Command boundary (atomic within AG3):** create Transaction (PENDING); apply a gateway status update
  (PENDING/AUTHORIZED → PAID/CANCELLED/REFUNDED); create the overpayment child; mark reconciled
  (bank date/VS, sent-to-bank flag). **Not atomic / dangerous today:** the PAID transition runs a large
  fan-out (campaign recompute + cascade save, recurring/voucher promotion, role grant, email+Slack, ES
  enqueue) inside the entity save from every write path with no callback idempotence and re-entrant saves
  — **HS03**; the callback route is effectively public with no HMAC — **HS12** [FLW0003 §Side-Effects;
  FLW0006/0007].
- **Owning SRV:** Payment-Processing (domain) with ComGate/Netopia/MAIB adapters; RecurringPayment- and
  Reconciliation-Processors on the cron/import paths; primary **UC0005** (donate), **UC0006** (callback),
  **UC0007** (recurring), **UC0008** (reconcile).
- **Evidence / Confidence:** EN0009; INV01/07/08/10/21/25; FLW0003/0004/0005/0006/0007/0011/0012/0013.
  **Confirmed**; REFUNDED reachability is **Hypothesis** (refund path not deep-mined) [§3.3].

### AG4 — RecurringTransaction (subscription schedule) · root **EN0010**

- **Root / lifecycle anchor.** A subscription schedule + gateway token. Created **inactive** with the
  first payment and activated (flag 0→1) only when that Transaction reaches PAID (**INV08**); a cron then
  charges it periodically, each charge creating a **new child Transaction in AG3** (**INV09**) [EN0010
  Lifecycle; §3.4].
- **Members:** none. Its sole relation is to its originating Transaction (AG3) — a schedule cannot exist
  without one (INV08), but the Transaction is a separate aggregate root, so RecurringTransaction is
  modelled as its **own** root that *references* AG3, not as a member of it. This is the "decide whether
  recurring is its own root that spawns Transactions" question: **it is its own root; it spawns child
  Transactions into AG3** [INV09].
- **Invariants:** INV08 (activation depends on linked Transaction PAID), INV09 (each cron charge spawns a
  child Transaction; due-selection depends jointly on schedule + parent Transaction), INV28 (cancellation
  writes a timestamp; whether it flips the active flag is **Hypothesis**).
- **Command boundary (atomic within AG4):** create schedule (inactive); activate on PAID (idempotent);
  set gateway token (Netopia); advance last-charge timestamp on a successful charge; cancel. The **charge
  itself** writes into AG3 (a new Transaction) and is therefore cross-aggregate — and books money
  optimistically as PAID on a non-throwing gateway call — **HS04** [FLW0007].
- **Owning SRV:** RecurringPayment-Processor + Payment-Processing; primary **UC0007**, participates in
  UC0006.
- **Evidence / Confidence:** EN0010; INV08/09/28; FLW0006/0007/0003/0004/0005. **Confirmed** for
  create/activate/charge; cancellation semantics **Hypothesis** (INV28) [§3.4].

### AG5 — Contract (legal document) · root **EN0011**

- **Root / lifecycle anchor.** A generated legal document with a two-step e-signature; it has **no status
  enum** — signature progression is expressed by stamped fields (draft → manager-signed →
  fundraiser-signed) [EN0011; §3.6].
- **Members:** none. **ContractTemplate (EN0012)** is the *reference* source it is rendered from, not a
  member (see §3). TaxPayer (EN0015) pairs *to* a Contract but is its own record (AG11).
- **Invariants:** INV11 (signature progression **drives the owning Application's** state
  contract → waiting_signature → contract_signed — cross-aggregate coupling to AG1), INV22 (per-year
  sequential numbering, app-level uniqueness only — race-prone), INV26 (a RO TaxPayer pairs with exactly
  one redirect Contract — **Partial**).
- **Command boundary (atomic within AG5):** generate Contract (render body → PDF, assign number); manager
  signs; fundraiser signs (signature blob + hash + QR confirmation PDF). The signature **side-effect on
  the Application** (INV11) crosses into AG1; numbering is not DB-guarded (INV22).
- **Owning SRV:** Document-Generation-&-Fulfilment; primary **UC0004** (contract & signature), UC0010 (tax
  documents).
- **Evidence / Confidence:** EN0011, EN0012; INV11/22/26; FLW0008. **Confirmed** for signature flow;
  no voided/cancelled state evidenced (Open Question) [§3.6].

### AG6 — Voucher (Dobrošek) · root **EN0013**

- **Root / lifecycle anchor.** A prepaid gift code with **two orthogonal boolean dimensions**: paid/
  published (flips on the purchasing Transaction reaching PAID) and redeemed (flips when applied to a
  Story) [EN0013; §3.5].
- **Members:** none. Owner is *derived* from the purchasing Transaction (AG3); the redemption Story is a
  Campaign (AG2) — both are references, not members [EN0013 Relations].
- **Invariants:** INV10 (both dimensions coupled to Transaction/Campaign: paid on Transaction PAID;
  redeemable only if paid & not-applied, and redemption re-points the linked Transaction's campaign),
  INV24 (voucher code has no DB unique key; check-then-set on the redeemed flag is TOCTOU-race-prone).
- **Command boundary (atomic within AG6):** generate voucher(s) (on Transaction PAID with voucher data);
  promote to paid; redeem/apply to a Story. Redemption's **re-pointing of the linked Transaction's
  campaign** crosses into AG3 (INV10); the redeemed-flag set is not transaction-guarded (INV24).
- **Owning SRV:** Document-Generation-&-Fulfilment (+ Payment-Processing on purchase); primary **UC0009**,
  participates in UC0006.
- **Evidence / Confidence:** EN0013; INV10/24; FLW0018/0003. **Confirmed** for paid/redeem; any expiry
  lifecycle is **Hypothesis** (no job mined) [§3.5].

### AG7 — Party (User + Contact) · root **EN0008 User**

- **Root / lifecycle anchor.** The User is the first-class Party and ownership/authorship anchor
  referenced by nearly every entity; differentiated by **role**, not by a status enum [EN0008;
  DOMAIN-kernel §1]. Chosen as root because it is the identity anchor and because Contact is provisioned
  and hard-deleted *with* its owning User (INV12, INV17).
- **Members:**
  - **EN0006 Contact** — *composed party-detail record, but a shared mutable store*. A User points to a
    Contact; a Contact optionally back-links its owning User. Provisioned together with the
    User from an Application (INV12) and, destructively, hard-deleted together on dedup (INV17). **Caveat
    (HS08):** Contact is an *overloaded universal party store* representing child/fundraiser/patron/
    school/employer/lead disambiguated only by a discriminator, referenced cross-aggregate by AG1
    (Application child / lead_contact) and by ApplicationProfile — so although its lifecycle sits inside
    AG7, it is **shared mutable state read/written from AG1, AG8 and AG9** (the risk classification is
    written by Scoring, AG9). This is the single biggest cross-aggregate hazard — see consistency doc §3.
  - **EN0007 Account** — *composed but dormant*. A thin owner-scoped record holding a serialized ML
    classifier for the campaign-recommendation subsystem; **confirmed dormant (INV27)** — no live write
    path exercises it. Placed here as a User-owned satellite; a rewrite may drop it [HS14].
  - **EN0023 UserNote** — *composed annotation child*. A revisionable note referenced by exactly one
    Contact via the Contact's note slot; no lifecycle beyond create/revise [EN0023 Relations/Lifecycle].
- **Invariants:** INV12 (User+Contact provisioned as a lifecycle dependency of an Application; child
  Contact keyed/reused by national number, no User for the child), INV17 (Contact dedup reparents all
  references and hard-deletes the duplicate Contact **plus its owning User**, no transaction — HS09),
  INV21 (first PAID Transaction grants the `supporter` role — a cross-aggregate write *into* AG7 from
  AG3), INV23 (no enforced Contact identity uniqueness — why dedup is manual), INV27 (Account/rec dormant).
- **Command boundary (atomic within AG7):** register/provision User+Contact; grant/adjust roles;
  authenticate; anonymise (GDPR); attach/revise a UserNote; dedup-merge Contacts (reparent + delete).
  **Not atomic / dangerous today:** GDPR erasure only blanks-in-place and re-upserts to Mautic (**HS06**,
  anti-erasure); dedup runs with no transaction/dry-run and hard-deletes Users (**HS09**); the
  `supporter` role grant is written from AG3's payment save (INV21, cross-aggregate).
- **Owning SRV:** Party-&-Contact-Management + Identity-&-Access; primary **UC0014** (auth), **UC0016**
  (party records / dedup), **UC0015** (GDPR), UC0001 (provisioning).
- **Evidence / Confidence:** EN0008, EN0006, EN0007, EN0023; INV12/17/21/23/27; FLW0010/0014/0015/0020/
  0023/0026. **Confirmed** for the party cluster; Account is **Confirmed-dormant**; the Contact
  risk-classification transition table is **Partial** [§3.7].

### AG8 — Organisation (employer registry) · root **EN0018**

- **Root / lifecycle anchor.** An employer/partner registry carrying a worker roster (Users with role
  `organisation_worker`, each with an admin flag) and synced daily to an external Elasticsearch index
  [EN0018].
- **Members:** none composed exclusively. Its **worker** links point to Users in **AG7** by reference (the
  Users are their own party aggregates); it references a Contact and can hold a logo. Modelled as its own
  root because it has an independent lifecycle (create, worker provisioning, dedup, daily sync) and is
  referenced *by* Application/ApplicationProfile (as the patron's employer), not owned by them.
- **Invariants:** INV18 (on Organisation dedup only the Application patron-employer reference is
  reparented; any other reference — worker links, contacts — is **left dangling**; no transaction).
- **Command boundary (atomic within AG8):** create/edit Organisation; provision a worker (creates/roles a
  **User in AG7**, cross-aggregate); merge duplicates (reparent employer ref + delete); daily ES upsert.
  **Not atomic today:** worker provisioning writes a User (cross-aggregate, AG7); dedup reparents only one
  reference and leaves others dangling (INV18, HS09).
- **Owning SRV:** Party-&-Contact-Management; primary **UC0016** (org merge sub-flow), UC0018 (index sync).
- **Evidence / Confidence:** EN0018; INV18; FLW0024. **Confirmed**; the org-admin capabilities of a worker
  are not evidenced (Open Question).

### AG9 — Risk assessment (Scoring + Blacklist) · root **EN0017 ScoringRecord**

- **Root / lifecycle anchor.** The scoring outcome. Its **primary live representation is JSON attached to
  the Application** (manual scoring snapshot + auto low-risk recalc); a separate carrier entity is
  **defined but dormant / has no writer** [EN0017]. Modelled as an aggregate distinct from AG1 because
  scoring is a bounded-context capability (C2 Risk) with its own command surface, even though its live
  data physically rides on the Application record.
- **Members:**
  - **EN0016 Blacklist** — *composed classification child*. Each Blacklist entry **requires** an
    Application and records a white/black classification against a person role; created by the scoring
    workflow [EN0016 Relations/Lifecycle; INV15]. Immutable once written (no delist path evidenced).
- **Invariants:** INV15 (a scoring approval creates Blacklist entries linked to the Application **and**
  propagates the classification onto the matching Contact by a raw email-keyed update **with no LIMIT** —
  a cross-aggregate write into AG7's Contact, HS08), INV16 (the derived low-risk score on the Application,
  with the fundraiser-profile owner-coupling defect).
- **Command boundary (atomic within AG9):** manual score → persist the scoring outcome on the Application
  (+ set `scoring_ok` only from `scoring`), create Blacklist entries, set the Contact risk/blacklist
  classification; auto low-risk recalc on `to_check`; coordinator low-risk override. **Not atomic /
  dangerous today:** the classification
  write onto Contact is a raw update by email with no LIMIT (can touch multiple Contacts, HS08), and it
  writes across AG9 → AG1 (Application state) → AG7 (Contact) in one non-transactional flow (INV15).
- **Owning SRV:** Scoring-&-Risk (delegating to MVCR / ARES verification adapters); primary **UC0003**,
  participates in **UC0002** (the `to_check` recalc).
- **Evidence / Confidence:** EN0017, EN0016; INV15/16; FLW0016/0017. **Confirmed** for the live
  Application-attached scoring path; the separate scoring carrier entity is **Hypothesis/dormant** (no
  writer) [EN0017 Lifecycle].

## 5. Notes & hypotheses

- **Hypothesis-marked aggregate decisions** (evidence weak / not fully mined):
  - **AG2 · CampaignLog (EN0028) membership** — assigned as a Campaign audit child, but **no writer is
    evidenced**; whether it is written on Campaign field changes is `Hypothesis` [EN0028 Lifecycle].
  - **AG4 · RecurringTransaction cancellation** — that cancellation flips the active flag (vs. only
    stamping a timestamp) is `Hypothesis` (INV28); the cancel write path was not mined.
  - **AG9 · ScoringRecord carrier entity** — the live scoring data is Application-attached JSON; the
    separate scoring carrier is **defined but dormant / no writer** (`Hypothesis`) [EN0017].
  - **AG11 · TaxPayer↔Contract pairing** — INV26 is `Partial`; the RO create/sign path is not deep-mined.
  - **AG7 · Account (EN0007)** — placed as a User satellite but **confirmed dormant** (INV27); a rewrite
    may legitimately drop it. Its membership is a modelling placement, not live coupling.
- **Roots that are "their own root but spawn/act on another aggregate" (deliberate decisions):**
  - **RecurringTransaction (AG4) is its own root and spawns child Transactions into AG3** (INV09) — it is
    *not* a member of the Transaction aggregate, because a schedule outlives any single charge.
  - **Voucher (AG6)** and **DonationConfirmation (AG10)** reference/aggregate over Transactions (AG3) but
    are separate roots (INV10, INV02).
  - **Scoring (AG9)** physically stores its live state on the Application record yet is modelled as a
    distinct risk aggregate (bounded context C2), because it has its own commands and its own child
    (Blacklist) and writes cross-aggregate (Contact classification, INV15).
- **Shared mutable state is the dominant hazard.** Contact (EN0006, HS08) sits in AG7 but is read by AG1
  and written by AG9; this is called out here and expanded in CONSISTENCY-boundaries §3. It is the primary
  reason a rewrite should split party roles and add real identity constraints (INV23).
- **No boundary is transaction-enforced today.** All aggregate members are linked by soft references (no
  DB FKs), and the most important cross-aggregate flows (payment→campaign completion, status fan-out,
  dedup/merge, scoring classification) run as **non-transactional entity-save side-effects** (HS01, HS03,
  HS09). The aggregates above are the *logical* boundaries a rewrite should make transactional — see
  CONSISTENCY-boundaries §4 for the per-pattern guidance. These are current-state observations, not a
  redesign.
