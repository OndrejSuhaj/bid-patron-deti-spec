## 2. Debt classification

Every catalog item is classified. A **Rewrite Blocker** is a defect that would corrupt data, money, or legal
obligations if carried into the rewrite (or that makes the current behaviour impossible to preserve faithfully
without a design decision first). **Architectural Risk** = structural coupling/shape that a rewrite must
redesign but that is not itself data-destructive. **Legacy Debt** = present-but-inert/thin code that needs an
explicit drop/rebuild/mine decision. **Operational Risk** = runtime/ops hazard (secrets, guards, unbounded
files, alert-not-repair). Some items carry a secondary class.

## 3. ADR candidate list **[recommendation]**

> **This section is recommendation, not current-state fact.** Each ADR converts a major current-state finding
> (from §1) into an architecture decision the rewrite must take. Each states a **problem** (grounded in evidence),
> the **affected components** (SRV / context / EN / AG ids), and a **trade-off summary**. These are decisions to
> *make*, not patch plans; no implementation-level detail is prescribed. Grounded in `CONSISTENCY-boundaries §4`
> rewrite guidance (rows 1–13) and `DOMAIN-kernel §4` hotspots.

### ADR-01 — Adopt an explicit status-orchestration service + enforced transition table
- **Problem.** The ~66-state workflow is driven by unconditional, non-idempotent, non-transactional entity-save
  fan-out with no transition-legality guard on 2 of 3 forms — any state is reachable from any state
  (R01/R02; HS01/HS02; INV04; §3.1).
- **Affected components.** Application-Status-Orchestrator (O, SRV0002), Application-Lifecycle (D, SRV0001),
  ApplicationAction-Processor (P), context **C1**; AG1 (root EN0001); consumers Scoring-&-Risk (C2),
  Document-Generation (C6), Transactional-Messaging (C8).
- **Trade-off.** An authoritative, enforced transition table + idempotent guarded handlers gives enforceable
  legality and safe re-runs, at the cost of migrating ~66 states / ~40 transitions and re-expressing config-only
  rules as an explicit machine; terminal vs re-enterable states must be **decided** (currently undefined).

### ADR-02 — Replace entity-save side-effects with an explicit transactional command + domain events
- **Problem.** The PAID "money hub" and the App↔Campaign sync run as re-entrant, non-transactional save
  side-effects from every write path; a desync is alerted, not repaired (R03/R16; HS03; INV01/03/04/07/21;
  CONSISTENCY §2/§3.1–§3.2/§3.9).
- **Affected components.** Payment-Processing (D, SRV0007), Campaign-&-Story-Lifecycle (D, SRV0005),
  Application-Status-Orchestrator (O); contexts **C4 ↔ C3 ↔ C1**; AG3 → AG2 → AG1.
- **Trade-off.** Making PAID an atomic command in AG3 and publishing idempotent, out-of-band events for campaign
  recompute/completion, promotion, role grant, and messaging removes recursion/partial-graph risk and makes one
  aggregate the source of truth (reconcile-not-alert), at the cost of introducing an event mechanism and
  eventual-consistency semantics the current code does not have.

### ADR-03 — Charge recurring donations under a claim/lock with confirmed-settlement PAID
- **Problem.** The recurring cron optimistically marks PAID on a non-throwing gateway call, with no schedule
  lock and only a 28-day SQL window as dedup; CZ hardcodes the transparent account (R05; HS04; INV09; §3.4).
- **Affected components.** RecurringPayment-Processor (P, SRV0007/0008), Payment-Processing (D), the payment
  adapters (A); context **C4**; AG4 → AG3.
- **Trade-off.** Locking the schedule and confirming settlement before PAID prevents double-charge and
  unconfirmed-money booking, at the cost of a two-phase (pending→confirmed) charge model and durable per-charge
  idempotency keys replacing the time-window heuristic.

### ADR-04 — Isolate payment gateways behind a port + authenticate callbacks + enforce payment identity
- **Problem.** Three gateways are embedded per-vendor; callbacks are effectively public with no HMAC; payment
  identity has no DB unique key and donation creation has no idempotency key (R04/R06/R14; HS12; INV25;
  ES0001/0002/0003; SRV §4; CONSISTENCY §3.4).
- **Affected components.** ComGate-/Netopia-/MAIB-Adapter (A, SRV0008), Payment-Processing (D, SRV0007) behind a
  `PaymentGateway` port; context **C4**; AG3.
- **Trade-off.** One port + per-vendor adapters, authenticated callbacks, a DB unique constraint on the payment
  identity tuple and an idempotency key on donation creation make callbacks forgery/replay-resistant and money
  records duplicate-proof — at the cost of wrapping the strongest lock-in (Netopia's vendored SDK) behind the port
  and reworking the per-gateway status-mapping paths.

### ADR-05 — Introduce a canonical Party model with split roles + real uniqueness
- **Problem.** One overloaded Contact represents every party by a discriminator with no FKs and no uniqueness on
  national-number/phone/email; classification is a no-LIMIT email-keyed raw update (R07; HS08; INV15/23;
  ARCH0001 §8 Risk 2).
- **Affected components.** Party-&-Contact-Management (D, SRV0012), Identity-&-Access (D, SRV0015),
  Scoring-&-Risk (D, SRV0003); contexts **C7/C9/C2**; AG7 (root EN0008; member EN0006), EN0002.
- **Trade-off.** Splitting party roles and adding enforced identity constraints eliminates the duplicate
  accumulation that drives destructive merges and prevents cross-record classification overwrite, at the cost of
  a substantial data model + migration and re-scoping every soft reference that points at Contact today.

### ADR-06 — Decompose the Application/ApplicationProfile god-object and clarify field ownership
- **Problem.** Application ties ~20 soft references; ApplicationProfile holds ~100 fields twice; scoring reads the
  fundraiser profile for patron-side data (owner coupling); raw writes bypass the entity layer (R08; HS10;
  INV16/20).
- **Affected components.** Application-Lifecycle (D, SRV0001), Scoring-&-Risk (D, SRV0003); context **C1/C2**; AG1
  (EN0001, EN0002).
- **Trade-off.** Decomposing the aggregate and fixing field ownership makes the case record safe to change and
  removes surprising cross-profile derivations, at the cost of untangling deep field-level coupling and deciding
  the fundraiser-vs-patron profile split cleanly.

### ADR-07 — Make dedup/merge transactional, reversible-by-preview, and archive-not-delete
- **Problem.** All three merge paths (Contact dedup, lead pairing, organisation dedup) run with no transaction,
  no dry-run, hard-delete users/history, reparent only some references, and have no country/role scoping (R09/R10;
  HS09; INV17/18/19; CONSISTENCY §3.8).
- **Affected components.** Party-&-Contact-Management (D, SRV0012), Application-Lifecycle (D, SRV0001),
  Identity-&-Access (D, SRV0015); contexts **C7/C1/C8**; AG7/AG1/AG8.
- **Trade-off.** Wrapping merges in a transaction with a dry-run/preview, archiving instead of hard-deleting,
  routing Users through cancel/anonymise, and reparenting **all** references makes merges safe and GDPR-consistent,
  at the cost of building preview/rollback machinery and defining complete reparenting semantics (which the current
  single-reference merges never had).

### ADR-08 — Make GDPR erasure actually erase (and messaging asynchronous)
- **Problem.** Erasure only blanks-in-place and re-upserts the user to Mautic with names intact (downstream delete
  is a stub); transactional mail is sent synchronously in-save with no retry and untracked delivery (R11/R18;
  HS06/HS13; CONSISTENCY §3.12; ES0006).
- **Affected components.** Identity-&-Access (D, SRV0015), Transactional-Messaging-Orchestrator (O, SRV0013),
  Mautic-CRM-Adapter / Email-Adapter (A, SRV0014/SRV0013); contexts **C9/C8**; AG7.
- **Trade-off.** Real deletion/suppression cascaded downstream (including Mautic) plus asynchronous queued
  messaging with retry and tracked delivery satisfies right-to-erasure and stops a failing send from aborting a
  domain save — at the cost of decoupling send from save and reworking the anti-erasure re-upsert path.

### ADR-09 — Country-scope, permission-tighten and stop persisting reporting exports
- **Problem.** CSV exports dump cross-tenant PII to `/tmp` with no country filter, coarse authorization, no
  cleanup, no encryption, and stale same-day cache serving (R12; HS07; UC0017; BR-ReportingAndDataAccess).
- **Affected components.** CSV-Export-Processor (P), Reporting-ReadModel (D, SRV0010); context **C5**; read-models
  EN0031/EN0032; cross-cuts the tenancy decision (ADR-10).
- **Trade-off.** Country-scoped queries, a dedicated fine-grained permission, and non-persistent/cleaned exports
  close the cross-tenant PII leak, at the cost of building per-tenant scoping (which depends on ADR-10) and
  removing the current cache-serving shortcut.

### ADR-10 — Make CZ/RO/MD an explicit tenant dimension
- **Problem.** Country behaviour is expressed only via runtime branches + per-country hardcoding with no
  tenant/country column; some crons lack an environment guard; per-country templates/flows diverge (R13; HS11;
  ARCH0001 §2/§6/§8 Risk 4; INV26).
- **Affected components.** Cross-cutting across **all contexts**; especially Payment-Processing (C4),
  Bank-Reconciliation (C5), Campaign-&-Story-Lifecycle (C3), Document-Generation (C6), Reporting (C5);
  the payment/bank/tax adapters (A).
- **Trade-off.** A first-class tenant dimension on core entities and in scoping gives clean per-country isolation
  and enables ADR-09's scoping and per-country vendor routing, at the cost of a pervasive model change and a
  migration that must back-fill tenant onto today's un-tagged rows.

### ADR-11 — Isolate every external boundary behind a port (adapter-per-boundary)
- **Problem.** Vendor lock-in is embedded (Netopia vendored SDK, MAIB mutual-TLS, Mautic BasicAuth+per-country
  IDs, OneDrive ROPC, Elasticsearch hardcoded host/Bearer, Facebook CAPI, Slack/Telegram, MVČR/ARES) (R14;
  SRV §4; SRV-restructuring-actions §1 S1–S5; ES0001–0016).
- **Affected components.** The 16 target Adapter SRVs (A) across C2/C4/C5/C6/C8/C10/C11; ports owned by the
  corresponding Domain services.
- **Trade-off.** One adapter per external boundary behind a stable port makes vendors swappable and keeps
  per-region protocol detail out of the domain, at the cost of building/maintaining 16 adapters and defining port
  contracts for boundaries that today leak vendor specifics into domain code.

### ADR-12 — Harden reconciliation import legs; decide drop-or-rebuild for dormant/thin subsystems
- **Problem.** Reconciliation legs are non-idempotent and lossy (skipped-day, row-capped match, brittle parse,
  unstable key); the recommendation subsystem is dormant and the FB inbound webhook is a not-implemented stub;
  search-index/scheduled-publish/ops-alert flows are un-mined (R15/R19/R20; HS05/HS14/HS16;
  UC-srv-traceability §4; INV27).
- **Affected components.** Reconciliation-Processor (P) + Moneta-AISP-/BankMail-IMAP-/ComGate-TransferSync-Adapter
  (A) in C5; CampaignRecommendation-Processor (P, dormant) in C3; SearchIndex-Processor/Elasticsearch-Adapter
  (C10), Workflow-Engine/ScheduledPublish-Processor/Ops-Logging-Adapters (C11); AG3/AG12/AG13/AG7.
- **Trade-off.** Making each import leg retryable/idempotent (durable cursor, unique dedup, robust parse) closes
  the silent money-data-loss window; an explicit drop-or-rebuild decision per dormant/thin feature prevents
  building inert code as live behaviour — at the cost of first **mining** FL055/FL057/FL059 and resolving the
  transfer-sync scheduling conflict before those SRVs can be relied upon.
