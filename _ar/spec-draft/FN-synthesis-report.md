## 1. Active rules & template used

Authored under the following normative sources (precedence: glossary → cross-layer discipline →
layer rules → template; task overrides a formatting detail only for this run):

- `tooling/docs/rules-FN.md` — FN describes *system capabilities, not workflows*; references
  UC/EN/ES/MSG by `doc_id`; no implementation code, no framework configuration.
- `tooling/docs/cross-layer-discipline.md` — single-source ownership: FN owns *internal functional
  capabilities and responsibilities* and references (never inlines) rule content (→BR), entity
  attributes (→EN), and flows (→UC). The >50-character near-verbatim restatement of another layer's
  owned content is a violation.
- `tooling/templates/template-FN.md` — section order: Purpose / Responsibilities / Related Use Cases
  / Related Entities / Integrations / Constraints, with frontmatter
  `doc_id, title, canonical_layer: FN, spec_type: functional-capability, status`.
- `_ar/repo-map/glossary.md` — canonical terminology (Application/Žádost, Story/Příběh,
  Campaign, Patron, Voucher/Dobrošek, Lead, status-vocabulary values).

Hard rules enforced: no invented capabilities; **no code-level detail** (no
file/class/method/route/controller/repository/queue names, no `.php`, no `::`); do **not** mirror
SRV 1:1; do **not** mirror FLOW 1:1 — cluster into meaningful capabilities. Status-vocabulary values
(PAID, to_check, scoring_ok, campaign_uncompleted, PENDING/AUTHORIZED/CANCELLED/REFUNDED) and named
integrations (ComGate, Netopia, MAIB, Mautic, ARES, MVČR, Moneta, OneDrive, Elasticsearch, Slack,
Telegram, Facebook, GTM, WhoisXML, Nager.Date) are allowed literals. Reconstructed strictly from AR
artifacts — Patronus source under `intake/current-solution/_source/` was **not** read.

## 4. Capabilities kept broader than expected + why

- **FN0001 Application Intake & Case Management** — the Lead phase and the Application phase are the
  *same record* (~66 statuses on one state field), so intake, questionnaire profiles and role-scoped
  access sessions are one capability rather than a separate "lead" capability.
- **FN0002 Status Orchestration** — kept as one seam even though it fans out to messaging, sessions,
  risk recompute, document generation and indexing, because in current state those are a single
  synchronous in-save side-effect, not separable services.
- **FN0003 Scheduled Status Transitions** — the cron flow (FL009) was never mined; cadence and error
  handling are inferred from the EN0027 rule configuration only. Kept broad and marked Partial.
- **FN0005 / FN0008 / FN0012** — **adapter-family clusters** (see §5): CZ registry adapters, per-region
  payment gateways, and the three reconciliation sources are each one capability, not one FN per adapter.
- **FN0014 Party Management + Merge** — the overloaded Contact registry, the Organisation registry and
  all three merge sub-flows (contact / organisation / lead) are one capability rather than one FN per
  merge type, because they share the same destructive, non-transactional, reparent-then-delete shape.
- **FN0022 Search Indexing** and **FN0023 Operational Alerting & Audit** — infrastructure capabilities
  reconstructed largely from side-effect appearances in other UCs; their dedicated flows (FL055, FL059)
  were un-mined. Kept broad and marked Partial. *[Batch-4 update 2026-07-03: FL055→FLW0032,
  FL059→FLW0034 now mined — Confirmed; residuals: drain scheduling, ES audit.]*
- **FN0025 Workflow / Transition-Legality Engine** — the scheduled-publish flow (FL057) was un-mined
  *[Batch-4 update 2026-07-03: now mined FLW0033 — Confirmed for the scheduled-publish sub-flow]*
  **and** transition-legality is not actually enforced on the live change forms today; this capability
  is largely a target-shape reconstruction of a gate that current state does not truly apply. Kept
  broad and explicitly flagged as not-confirmed current behaviour.
- **FN0026 Reference Data & Geographic Lookup** — kept minimal-but-standalone: it owns no aggregate and
  appears in no dedicated flow, but is included so the reference-data SRV and its UC0001/UC0022 touches
  are covered without inventing behaviour.

### 5b. FN does NOT mirror SRV 1:1 (clustering confirmed)

19 SRV services (SRV0001–SRV0019) were synthesized into 26 FN capabilities, but the mapping is a
deliberate **re-cluster**, not a rename — several SRV services span multiple FNs and several FNs draw
on multiple SRVs:

- **Adapter families collapsed into one capability each** (the primary anti-mirroring move):
  - **FN0005** = ARES-Registry-Adapter + MVCR-DocValidity-Adapter (from SRV0004).
  - **FN0008** = ComGate + Netopia/MobilPay + MAIB adapters (from SRV0008) — one "Payment Gateway
    Integration" capability spanning all three per-region adapters.
  - **FN0012** = Moneta-AISP + BankMail-IMAP + ComGate-TransferSync (from SRV0009) — three
    reconciliation source adapters as one capability.
  - **FN0023** = Slack + Telegram + Elasticsearch-audit transports (from SRV0018).
- **One SRV split by concern across FNs:** SRV0011 (Document-Generation-&-Fulfilment) → FN0009
  (contract rendering) + FN0013 (tax/confirmation docs) + partly FN0011 (voucher). SRV0014
  (Marketing/Analytics/Lead) → FN0015 (Mautic CRM) + FN0016 (Facebook/GTM/CAPI + Lead Ads). SRV0015
  (Identity-&-Access) → FN0018 (identity/access) + FN0021 (GDPR anonymisation). SRV0007 →
  FN0007 (money hub) + FN0010 (recurring). SRV0017 (Platform-Kernel/Workflow) → FN0025 (workflow gate
  + scheduled publish) + FN0026 (reference data).
- **Merge sub-flows collapsed:** the three party-merge sub-flows (FLW0023/FLW0024/FLW0025) are one
  capability, FN0014, rather than one FN per merge type.

FLOW is likewise **not** mirrored 1:1: 30 FLW dossiers + several un-mined flow ids feed the 26 FNs as
evidence, clustered by capability (e.g. FLW0003/FLW0004/FLW0005 all inform FN0008; FLW0001/FLW0002 the
FN0002 fan-out; side-effect appearances in FLW0001/FLW0002/FLW0021/FLW0024 reconstruct FN0022).

## 6. Missing downstream artifacts that weaken capability definitions

The following layers are **not yet built**, and their absence leaves the noted FN references as
forward pointers that cannot fully resolve within the current draft set (recorded as Open Questions
per cross-layer discipline §7, not back-filled):

- **MSG (transactional messages)** — **not built.** FN0002, FN0009, FN0011, FN0013, FN0019 all trigger
  or hand off transactional messages but can only name the *trigger*; the message contract
  (trigger → recipients → content → channel) has no `MSGxxxx` to cite. FN0002's draft currently carries
  an MSG placeholder in its references. The Notification Matrix in `intake/test-scenarios/` is the
  eventual evidence base for MSG.
- **ES (external systems)** — **not built.** Every integration in the map (ComGate, Netopia, MAIB,
  ARES, MVČR, Moneta, IMAP, OneDrive/Graph, Mautic, Facebook, GTM, WhoisXML, Nager.Date,
  Elasticsearch, Slack, Telegram) is named in the FN Integrations sections but has no `ESxxxx`
  integration-boundary document to reference. FN0005/FN0008/FN0012/FN0015/FN0016/FN0017/FN0019/FN0022/
  FN0023 are the most affected.
- **BR (business rules)** — **not built.** Several FN Constraints sections skirt domain-policy content
  that BR will own (e.g. publish-readiness gate conditions, overpayment-split rule, first-PAID role
  grant, scoring gate thresholds, RO working-day deadline rule). These are stated as capability
  constraints, not as canonical rules; once BR exists, FN should cite `BRxxxx` and drop any inline
  policy phrasing to satisfy the >50-char restatement rule.
- **ACL / API / JOB / QUERY (04-closure layers)** — not built. FN0018's role model (→ACL), the
  gateway callback contracts in FN0008 (→API), the cron/queue drains in FN0003/FN0010/FN0012/FN0020/
  FN0022/FN0022 (→JOB), and the reporting read-model in FN0020 (→QUERY) will be sharpened once those
  contracts exist; today they are described only at capability altitude.
