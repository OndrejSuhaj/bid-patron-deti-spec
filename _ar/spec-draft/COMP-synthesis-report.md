## 1. Active rules / template used

- `tooling/docs/rules-COMP.md` — governing rules for this layer. Hard rule enforced throughout:
  a `COMPxxxx` is created **only when reuse is observable across ≥2 WIRE screens/screenshots**; if
  reuse cannot be evidenced, the element stays a WIRE `inline` entry — no component was invented.
  Each COMP's six required states (idle/hover/focused/disabled/loading/error) are addressed or
  explicitly marked `N/A`/`Uncertain`; unobservable accessibility (ARIA/keyboard/focus/SR) is
  recorded as `Uncertain` / Open Question, never fabricated.
- `tooling/templates/template-COMP.md` — section skeleton used for every written COMP doc: Purpose,
  Props/Inputs, Variants, States, Events, Accessibility, Usage Constraints, Dependencies,
  Composition, Examples, Evidence (Open Questions added per §5 of cross-layer-discipline.md, since
  several COMPs carry non-trivial open items).
- `tooling/docs/cross-layer-discipline.md` — single-source-of-truth discipline followed throughout:
  no WIRE layout, COPY text, EN attribute definitions, or ACL rules were inlined into any COMP;
  entity-typed props cite `ENxxxx` by reference only (`EN0001`, `EN0004`, `EN0005`, `EN0006`,
  `EN0008`, `EN0021`), never restating their attribute definitions.
- `_ar/repo-map/glossary.md` — consulted for terminology; no new domain terms were coined by this
  pass (COMP is a UI-shape layer, not a domain-vocabulary layer).

## 3. Candidates left inline, and why

`_ar/spec-draft/WIRE-synthesis-report.md` §6 seeded 8 candidate patterns; two were **not** promoted
as originally framed, and several additional candidates surfaced during this pass were also
evaluated and rejected. Full list and rationale is in `COMP-inventory-map.md` under "Left inline —
candidates considered but NOT promoted." Summary:

- **Secondary/outline CTA button** — visual identity (color/fill/underline-vs-button) is
  inconsistent across its few occurrences; promoting would overstate reuse-as-identical. Recorded as
  an Open Question on `COMP0001` instead of a separate COMP.
- **Category/tag pill badge** — its only potential second occurrence (blog tags, S013/S014) has no
  WIRE file at all (blocked-no-uc), so the ≥2-*WIRE*-screen bar is not met by written docs even
  though the concept recurs visually. Left inline on `WIRE0001`.
- **Region map, testimonial carousel, voucher denomination card** — each observed on exactly one
  written WIRE screen (their nominal "second" screens — S005 for the voucher card — have zero
  captured evidence, so reuse cannot be confirmed, only asserted). Left inline.
- **FAQ accordion** — appears on 2 screens (`WIRE0006`, `WIRE0008`) but both show only the
  collapsed state, and `WIRE0008` explicitly flags its own expand behavior as "Assumed, not
  captured" — promoting a component whose defining interaction (expand/collapse) is entirely
  unevidenced was judged to overstate certainty. Left inline on both screens as a conservative call,
  a stricter reading of the evidence-gate than the WIRE report's seed list implied.
- **Generic single-line text `<input>`** — deliberately not promoted anywhere, despite near-universal
  reuse, because it carries no distinctive shared visual/interaction identity beyond native HTML
  input styling; COMP is reserved for genuinely reconstructed reusable *components*, not every
  primitive form control.
- **Amount/currency input, related-story sidebar card, account-dashboard mockup cards, zone-screen
  chrome on WIRE0005/WIRE0021/WIRE0022/WIRE0023** — each has a specific evidentiary weakness
  (duplicate-field ambiguity, single-screen occurrence, source screen itself Hypothesis/unconfirmed,
  or the *consuming screen's own* header/footer row marked "Assumed present" rather than Confirmed)
  documented per-candidate in `COMP-inventory-map.md`.

No component was invented to "complete" a pattern; every rejection above is evidence-driven, not a
coverage gap left unexplained.

## 4. Unobservable states / accessibility marked Uncertain

Per `rules-COMP.md`'s evidence convention, the following were **not** fabricated and are recorded as
`Uncertain`/`Assumed`/Open Question in the relevant COMP file rather than guessed:

- Every component's hover and focused states (no capture shows any hover/focus styling).
- Disabled-state rendering for COMP0001 (button), COMP0006 (checkbox), COMP0007 (dropzone) — no
  screen captures a disabled control.
- Loading states for COMP0001 (in-flight submit), COMP0007 (upload progress), COMP0009 (in-flight
  submission) — no async/spinner UI was ever captured.
- Error-state rendering for COMP0001 (validation errors surface on fields, not the button itself —
  recorded as `N/A` with rationale, not `Uncertain`), COMP0006 (unchecked-but-required error look),
  COMP0009 (invalid-email / throttling error look).
- COMP0004's `dismissed` lifecycle state and COMP0007's `filled` lifecycle state (files actually
  attached) — both `Assumed` from standard UI convention, explicitly flagged as not evidenced by any
  before/after capture.
- All four Accessibility sub-items (ARIA role, keyboard navigation, focus management, screen reader)
  across all 9 components — uniformly `Uncertain`, with COMP0009 additionally flagging the
  placeholder-as-label pattern (no visible `<label>` element) as a specific, named accessibility
  Open Question rather than a blanket "unknown."
