## 1. Active rules & template used

Authored under the following normative sources (precedence: cross-layer discipline → layer rules →
template; the driving-agent task refines merge/scope decisions only for this run):

- **`tooling/docs/rules-ES.md`** — an ES describes a system **outside** the platform boundary and
  defines only: system role, integration context, and interaction boundaries. It does **not** define
  business behavior. Forbidden content: implementation code, API payload/field definitions,
  framework config, controller/service names, file paths, library names. Frontmatter carries
  `doc_id / title / canonical_layer: ES / spec_type: external-system / status`, with `references`.
  Recommended structure: **Purpose · System Overview · Integration Model · Data Exchange · Constraints.**
- **`tooling/docs/cross-layer-discipline.md`** — single-source ownership: ES owns external-system
  integration boundaries and conceptual data exchange. It **references** ARCH (context) by `doc_id`
  and never restates entity attributes (→ EN), contract payloads (→ API), or rule content (→ BR);
  the >50-character restatement rule applies.
- **`tooling/templates/template-ES.md`** — the per-file skeleton used for all 16 ES files.

Key merge / scope rules applied this run:

- **One external service = one ES**, even when Patronus reaches it through several adapters,
  interaction modes, endpoints, or use-cases.
- **Internal subsystems are not ES** — only the external vendor/service is.
- **Named integrations and status vocabulary** (ComGate, MAIB, PAID, PENDING, aviz, Dobrošek, …)
  are allowed literals.
- **Current-state only** — the target assignment (`it-zadani`) is out of scope.

## 2. Systems discovered (count + themes)

**16 external systems** were finalized, corresponding to the **17 integration-landscape boundary
rows** in `ARCH0001` §5 after same-vendor merges (see §3). Themes:

| Theme | Systems | Notes |
|-------|---------|-------|
| **Payment gateways (per region)** | ES0001 ComGate (CZ), ES0002 Netopia/MobilPay (RO), ES0003 MAIB (MD) | One gateway per region; capture donation payments (incl. RO recurring). Callbacks effectively public / no HMAC; vendor lock-in strongest for RO (vendored SDK) and MD (mutual-TLS cert). |
| **Bank / settlement reconciliation sources (CZ)** | ES0004 Moneta (AISP), ES0005 client IMAP inbox (aviz), ES0001 ComGate settlement mode | Feed incoming bank credits / payout listings into the reconciliation capability (FN0012). CZ-only; each is a distinct external boundary. |
| **Marketing / CRM / analytics** | ES0006 Mautic, ES0007 Facebook, ES0008 Google Tag Manager | Mautic also doubles as the transactional-mail transport. Facebook + GTM carry marketing/analytics signals only (no domain impact on failure). |
| **Registry / identity / validation checks** | ES0009 WhoisXML (email-domain), ES0010 ARES (CZ business registry), ES0011 MVČR (CZ ID-document), ES0012 Nager.Date (RO public-holiday) | Synchronous lookups feeding validation/scoring gates. ARES/MVČR are CZ-only; Nager.Date is RO-only and fail-open. |
| **External storage / index / files** | ES0013 Microsoft Graph/OneDrive (invoice import), ES0014 Elasticsearch (search index + audit store + Elastic Cloud org index) | OneDrive is an inbound CLI pull; Elasticsearch is a single vendor boundary with three distinct current uses. |
| **Operational alerting (ops, not user messaging)** | ES0015 Slack, ES0016 Telegram | Best-effort logger alerts on error severity; carry the Application↔Campaign desync warning (INV04). Failure impact = alert loss only. |

Cross-cutting observations, current-state:

- **Regionalisation is pervasive at the ES boundary** — payment, reconciliation and registry checks
  differ per country (CZ / RO / MD), and several checks have no RO/MD equivalent.
- **Failure severity splits cleanly** into money/domain-impacting integrations (payment gateways,
  reconciliation sources, invoice import, Mautic transactional send) versus signal-only integrations
  (Facebook, GTM, Slack, Telegram) whose failure loses only marketing/analytics/ops signal.
- **Synchronous-in-save coupling** recurs (Mautic transactional send; ARES lookup with no timeout),
  where a slow/failing external call can block or abort the enclosing persistence.

## 4. Uncertain integrations

- **SmartMailing vs. Mautic (open naming question).** The integration inventory names a
  `patron_base.smartmailing`-style transactional-dispatch service alongside Mautic, while the
  reconstructed evidence treats **Mautic** as the actual CRM store and the actual mail transport.
  Rather than split a second "SmartMailing" ES on an unresolved name, this is documented as **one
  Mautic ES (ES0006)** with the naming question recorded in-file. `Conflict — requires
  clarification` on whether "SmartMailing" is a distinct external service or an internal alias for
  the Mautic transport. (Sources: integrations.md §2–§3.)
- **Facebook inbound Lead Ads intake.** The subscription handshake exists but ingestion is a
  confirmed not-implemented stub → **Status: Planned / Not Implemented** (HS16). Recorded inside
  ES0007, not as a live boundary.
- **Elasticsearch search-index sync flow (Partial).** The genuinely-async search-index path is
  confirmed only as a save-time side-effect; its core sync flow is **un-mined** (Partial, HS16).
  Boundary confirmed; internal orchestration incomplete.
- **Slack/Telegram alert-listener flow (Partial).** The alert-listener flow is un-mined, so the
  precise dispatch/failure behaviour beyond "best-effort, alert loss only" is not fully evidenced.

Confirmed **absences** (no uncertainty — treated as excluded, not open):

- **Firebase** — present only as a composer dependency plus a command that re-saves entities and
  prints an operator message; it makes **no** Firebase SDK call. `Uncertain` per integrations.md §5,
  excluded from the active external-system set.
- **SMS** — no dedicated SMS gateway exists in custom code (only a MobilPay SMS-payment request type
  inside the RO Netopia flow, which is part of ES0002). `likely none` per integrations.md §5.

## 5. Systems intentionally excluded (NOT external systems)

Per `rules-ES.md`, internal subsystems are **not** ES — only the external vendor is. Excluded:

- **Internal adapters / processors** — the per-region gateway adapters, the registry/identity
  verification adapters, the reconciliation processor, the SearchIndex processor, the messaging
  orchestrator, the CRM-sync queue worker, and the ops-logging adapters. These are Patronus-internal
  and are owned by the SRV/FN layers; the ES they reach across the boundary is documented instead
  (e.g. Elasticsearch is ES0014; the SearchIndex processor is **not** an ES).
- **Platform-internal stores** — the primary relational database (MariaDB) and Drupal-managed file
  storage are inside the platform boundary, not external systems.
- **Firebase** — composer-only dependency with no SDK call (see §4).
- **SMS** — no dedicated gateway (see §4).
- **Dev-only mail plumbing** (e.g. a local MailHog SMTP sink) — development scaffolding, not a
  production external system.
