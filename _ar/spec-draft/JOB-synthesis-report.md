## 1. Scope & method

Synthesised the JOB (background execution contract) layer for Patronus. Inputs: the stable BA layers
(`_ar/spec-draft/FN/`, `ARCH/`, `BR/`, `UC/`, `ES/`, `MSG/`, `EN/`, `DOMAIN-*`) and the mined flow
dossiers (`_ar/evidence/flow/`). Per the closure-phase generation-grade requirement, **every contract
was verified against the actual Patronus Drupal 10 custom source** at
`intake/current-solution/_source/patronus/web/modules/custom/**` — the code/config is ground truth for
trigger cadence, input scope, side effects, and failure semantics; the prose spec is context.

Candidate discovery was exhaustive over three trigger families:

- `grep` for all `hook_cron` implementations → **13 cron hooks** (one commented out).
- `grep` for all `@QueueWorker` plugins → **5 workers** (none carry a `cron` key).
- Enumeration of all `drush.services.yml` / `console.services.yml` command registrations and
  `src/Commands` + `src/Command` classes → operational CLI jobs separated from migration/one-off/test
  commands.

## 2. Result

**22 JOB contracts** documented (JOB0001–JOB0022), normalised from ~19 live cron/queue/CLI

## 3. Ground-truth findings that shaped the contracts

- **Master cadence is hourly, not per-job.** `docker-compose.yml:70` sets
  `CRONTAB: "0 * * * * drush ... cron"`. Every `hook_cron` job therefore fires hourly and daily jobs
  **self-throttle** via `\Drupal::state()` keys (seeded to fixed hours: 02:00 voucher/transaction,
  03:00 export, 04:00 recurring, 05:00 organisation). Jobs without a throttle (scheduled-publish,
  campaign deadline sweep, IMAP poll, application housekeeping, auto-transition, mautic drain,
  role-check) run on **every** tick. This is the single most load-bearing scheduling fact and is now
  explicit in every scheduler JOB's Trigger Model.
- **The only in-source crontab line for a specific job is MAIB.** `MaibCommands.php:62` carries the
  intended OS-cron entry `59 21 * * * ... drush @self.md-stag maib:close` — recorded verbatim in
  JOB0018. All other CLI jobs have **no evidenced schedule** (marked Hypothesis-on-scheduling).
- **Queues do not auto-drain.** No `@QueueWorker` has a `cron` key; `patron_search_cron` and
  `campaign_recommendation_cron` are commented out. So `es_upload_queue` depends entirely on an
  external invocation of `patron_search:process_queue` (JOB0022), and `mailing_queue` is bypassed
  altogether (USE_QUEUE off → synchronous send). Only `mautic_queue` is drained by a live cron unit
  (JOB0012). This drain gap is the residual Partial for FN0022 and the dormancy basis for JOB0014.
- **Whole-cron abort risk.** Several cron hooks (`export_csv`, `campaign`→insertState, `monetaapi`,
  `application`, `patron_base` mautic + scheduled-publish units, `comgate`/`netopia`) **re-throw** on
  error, so a single failing job can abort the whole hourly platform cron run. Captured per-JOB under
  Failure Handling; flagged as a cross-cutting operational hazard.
- **Non-transactional / weak-idempotency loops** are pervasive: recurring charge (no claim lock,
  double-charge window), Moneta import (last-run set before work → permanent day gap), scheduled
  publish (multi-write no transaction), search index (silent index gap on network failure; no
  delete-from-index), OneDrive import (duplicate attachment on re-run), ComGate sync (30-row cap).
  Each is recorded in its JOB's Idempotency / Failure Handling and cross-referenced to the owning
  DOMAIN/FLOW hazard, not restated.

## 6. Cross-layer discipline

Each JOB references FN/EN/ES/MSG/UC by `doc_id` and does not restate their content. Region gating
(CZ/RO/MD via Settings guards) is stated as trigger scope (a JOB concern), while the domain rules and
message content remain owned by BR / MSG. Redaction: all secrets (webhooks, tokens, gateway
passwords, index credentials) are shown as `<redacted>` per policy; the only concrete schedule quoted
is the non-secret MAIB crontab comment.
